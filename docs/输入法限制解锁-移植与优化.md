目标宿主：`com.baidu.input_oppo` / 百度输入法定制版 **8.5.303.494**（versionCode 8912，OnePlus 定制）。

## 3. 上游代码的性能问题（逐条）

上游是「恢复版」，其结构是 DexKit 特征匹配 + 运行时反射遍历。以下是按影响排序的问题清单。

### 3.1 DexKit 在输入法进程启动路径上同步跑十余次全量查询 ★★★★★

`HookEntry.handleLoadPackage` 里 `DexKitBridge.create(apkPath)` 之后连续 11 次 `bridge.findMethod`，
其中 `hookQuickPhraseEntryPoints` 一轮就有 5 个查询、`hookQuickPhraseLimitToastCaller` 还会
在 `resourceCallers` 基础上再做一次 `collectOnClickCallers`（`MethodData.callers` 又是一次 dex 查询）。

`DexKitBridge.create` 需要 mmap 并解析全部 dex 头；每次 `findMethod` 遍历方法表。
整体是**几百毫秒到秒级**的开销，且发生在 `handleLoadPackage` —— 输入法进程 fork 后立即执行，
直接等于键盘首次弹出延迟。

### 3.2 同一方法被多次 hook，回调叠加 ★★★★

`quick-phrase-click` / `quick-phrase-add-button` / `quick-phrase-add-button-direct` /
`quick-phrase-dialog-entry` 四个查询的条件高度重叠（都是 `onClick(View)` + 常量 100 +
`View.getId()` + `ArrayList.size()`）。`hookAll` 内部没有跨查询去重，命中同一方法时会
`XposedBridge.hookMethod` 多次 —— 一次点击触发多份回调，每份都完整 walk 一遍字段树。

### 3.3 运行时反射遍历字段树 ★★★★

`findListSlots` / `maskQuickPhraseMapLists` 每次点击都执行：

- `hostClassLoader.loadClass(field.className)`（每个字段一次，带 ClassLoader 锁）
- `findDeclaredField(...)`（`getDeclaredField` 每次复制一份 Field[]）
- 深度 ≤3 的递归遍历

这些是**纯静态信息**（哪个类的哪个字段装的是列表，与实例无关），却放在每次点击的热路径上。

### 3.4 无条件 hook 框架 `InputFilter$LengthFilter#filter` ★★★☆

`hookClipboardCopyNormalizer` 的 listeners 分支里，即使已经成功 hook 到宿主自己的
`String(String)` normalizer，仍然会调用 `hookClipboardFrameworkFilter()`。

`LengthFilter#filter` 是**进程内所有文本输入的必经方法**，hook 点是热路径。
（本机确实没有独立 normalizer，所以这一条在 8.5.303.494 上躲不开，但可以做到
「廉价前置判断」——见 §5.1。）

### 3.5 宽泛匹配「无参 void 方法」并常驻 hook ★★★

`hookQuickPhraseToastHelpers` 把 caller 调用的**所有** `void()` 无参方法全部 hook
（`caller.invokes.filter { it.returnTypeName == "void" && it.paramTypeNames.isEmpty() }`）。
这类方法极易命中无关的 getter 包装 / runnable，且每个都常驻 hook，
`beforeHookedMethod` 里用 `ThreadLocal.get()` 判断 armed。

而这一步的目的只是抑制「收藏太多啦」toast —— 列表已被 mask 成 99 条后，
宿主根本不会走进 toast 分支，这层保险是冗余的。

### 3.6 每次 `setDatas` 全量复制列表 ★★☆

`hookClipboardHistoryFilter` 无条件 `ArrayList(input.size)` + `addAll` 再包一层
`NoRemoveList`，`NoRemoveList.iterator()` 每次调用都新建包装对象。

### 3.7 反射构造 `AssetManager` 解析资源 id ★★☆

`resolveStaticResourceId` 通过反射 `new AssetManager()` + `addAssetPath(apkPath)` +
`new Resources(...)` 去查 `sym_collection_tip` / `iv_add_corpus` 的 id。
这会额外打开一份 `resources.arsc` 并常驻内存。

实际上 `R$string` / `R$id` 是公开类，直接反射读静态字段即可（零成本）。
本机这两个 id 更可以从宿主 `public.xml` 直接取常量。

### 3.8 每次点击做资源名解析 ★★

`isAddAction(view)` 在每次 `onClick` 里执行 `getResourceEntryName(view.id)` +
`lowercase()` + 7 次 `contains`。这是为了「候选方法有多个时过滤掉非添加按钮」——
属于把静态判定放到运行时。

### 3.9 日志用 `XposedBridge.log` ★★

`log()` 直接 `XposedBridge.log`（跨进程同步写），且字符串拼接在调用前求值 ——
即使不需要日志也要付拼接成本。上游有十余处每次点击 / 每次 mask 都打的日志。

### 3.10 `readQuickPhraseText` 全字段扫描 ★☆

`findObjectWithMethod(owner, "getEditText")` 遍历整个继承链的 `declaredFields`，
对每个字段值判断「是否有无参 `getEditText` 方法」。每次确认都做一次。

## 4. 两项「上游有、本机不需要」

### 4.1 剪贴板计数 `count()` → 1

上游 `hookClipboardCount` 把 `select count(_id) from clipboard` 的返回值直接改成 1，
注释是「expose the count as enabled」。

本机全库 `count()` 调用点（`px/g:56`、`px/n:194`、`px/w:1144`、`NoteBackupPref:59`、
`tm/f:139`、`e7/e`、`qx/f`、`xx/h`）**全部**只用于「清空剪贴板前判断是否为空」：

```java
if (qx.f.g(context).count() == 0) cp0.m.a(context, R.string.front_clip_clipboard_empty, 0);
else { /* 弹清空确认框 */ }
```

强制返回 1 的唯一效果是：**剪贴板真的为空时，点清空也会弹出清空确认框**（而不是提示"剪贴板为空"）。
纯副作用、零收益（上游那个宿主版本另有一套「剪贴板功能是否启用」判断，本机没有）。

**结论：不移植。**

### 4.2 历史快捷短语编辑目标解析

上游 `QuickPhraseSaver` 里有一层 `resolveEditIndex(list, marker, requestedIndexes)`：
先用「请求索引 + 文本 marker」匹配，再用「文本 marker」全表匹配 —— 因为它的自实现保存
不知道要改哪一条。

本机宿主保存逻辑是 `list.get(f12418k)`，`f12418k` 就是编辑索引（`-1` = 新增），
直接取，不存在「覆盖序号 0 条目」的问题。

**结论：本机不需要额外逻辑**（自实现保存里直接按 `f12418k` 取）。

## 5. 本实现的优化

### 5.1 静态定位表替代 DexKit（对应 §3.1）

`BaiduImeTargets` 把 6 个钩子点的类名 / 方法名 / 字段名 / 资源 id 全部写成常量，
注释里标出反编译行号。运行时：

- 零 `DexKitBridge.create`
- 零 `findMethod` 扫描
- 零 `System.loadLibrary("dexkit")`（本 Hooker 不加载 DexKit 的 so）

**代价**：宿主升级且混淆名变化时功能静默失效（只打日志，不崩溃、不影响宿主）。
考虑到本机是锁定版本（8.5.303.494 / 8912），这个取舍明确划算。
版本号在 `install()` 时打印进日志，便于日后排查。

### 5.2 每类一个钩子，跨查询无重叠（对应 §3.2）

6 个钩子点，彼此方法不同：

| 钩子 | 方法 | 触发频率 |
|---|---|---|
| 复制截断 | `ly.a#onPrimaryClipChanged` | 每次复制 |
| 复制截断（框架） | `InputFilter$LengthFilter#filter` | 每次文本过滤 |
| 历史过滤 | `px.u#setDatas(List)` | 面板刷新 |
| 条数上限（键盘） | `y90.p#onClick(View)` | 每次点击 |
| 条数上限（管理页） | `ImeOppoLazyCorpusActivity#onOptionsItemSelected` | 每次菜单 |
| 字数上限（输入） | `ww.a#onTextChanged` | 每次输入 |
| 字数上限（确认） | `dialog.b#onClick(DialogInterface,int)` | 每次确认 |

### 5.3 反射对象一次性解析（对应 §3.3、§3.10）

所有 `Field` / `Method` / `Constructor` 在 `install()` 阶段解析成对象并持有，
运行时只做 `field.get` / `field.set` / `method.invoke`。字段尽量**按类型**查找而不是按混淆名
（如键盘面板的 `Map` 字段、watcher 的 `int` 分派字段），降低改名风险。

### 5.4 高频钩子的廉价前置判断（对应 §3.4）

三个高频钩子的第一个判断都是最廉价的操作：

```kotlin
// LengthFilter（全进程热路径）：volatile 读 + 长度比较
if (!copyArmed) return chain.proceed()
val src = chain.getArg(0) as? CharSequence ?: return chain.proceed()
if (src.length <= 7000) return chain.proceed()

// onTextChanged（每次输入）：先比长度，超长才反射读字段
val text = chain.getArg(0) as? CharSequence ?: return chain.proceed()
if (text.length <= 300) return chain.proceed()
val which = whichField.getInt(holder)      // 只有超长才走这里

// onClick（每次点击）：直接比 id，不查资源名
if (view.id != ID_IV_ADD_CORPUS) return chain.proceed()
```

`copyArmed` 用 `@Volatile Boolean`（只需跨线程可见性）而非 `AtomicBoolean`，
省掉一次 CAS 语义的读。

### 5.5 不移植 toast helper 抑制（对应 §3.5）

列表被 mask 成 99 条后，宿主的 `else { toast }` 分支不会进入，无需抑制 toast。
少掉一整批「无参 void 方法」常驻钩子。

### 5.6 历史过滤直接包装（对应 §3.6）

不做「是否含超长条目」预检 —— 预检需要逐条反射 `Record.J()`（每次 ≈50ns × N 条），
比 `ArrayList` 纯引用复制（≈1µs / 300 条）更贵。`setDatas` 本身是低频调用，
复制产生的短命对象可忽略。

### 5.7 资源 id 用常量（对应 §3.7）

`R.id.add` = `0x7f0a009d`、`R.id.iv_add_corpus` = `0x7f0a078a`，
出自宿主 `resources/res/values/public.xml`，注释里标明出处。零反射、零 AssetManager。

### 5.8 日志走 LogUtils（对应 §3.9）

复用模块的 `LogUtils`（异步队列 + 总开关 + 按级别过滤），关闭日志时连字符串拼接都省掉
（`LogUtils.i` 内部先判 `loggingEnabled()`）。

### 5.9 按开关懒安装（本实现新增）

四个功能各自独立开关，`install()` 里逐项判断：

```kotlin
if (settingBoolean(KEY_COPY_LIMIT, false)) installCopyLimit(loader)
if (settingBoolean(KEY_CLIP_HISTORY, false)) installClipHistory(loader)
if (settingBoolean(KEY_CORPUS_COUNT, false)) installCorpusCount(loader)
if (settingBoolean(KEY_CORPUS_LENGTH, false)) installCorpusLength(loader)
```

**关闭的功能不 `loadClass`、不解析反射、不 hook**。四个全关时，输入法进程只多一次
版本日志 —— 这是本实现对宿主性能影响的下限。默认全关，用户按需开启。

## 6. 行为细节与副作用

### 6.1 复制放行窗口的竞态

`copyArmed` 在 `onPrimaryClipChanged` 前置置 true、后置置 false。
`LengthFilter#filter` 与 `onPrimaryClipChanged` 可能不在同一线程（前者 UI 线程，后者
ClipboardManager 回调线程），因此用 `@Volatile` 保证可见性。窗口极短（单次复制），
并发复制事件由 `ClipboardManager` 串行化，实际无竞态。

### 6.2 输入截断跳过时补副作用

`ww.a#onTextChanged` 的 case 0 除了截断，还负责 `clearIv`（清除按钮）显隐。
超长时跳过整个方法，因此手动补 `setVisibility(VISIBLE)` —— 超长必然非空，
等价于原逻辑的 `else` 分支。

### 6.3 条数 mask 的可见性

`BelowLimitList.size` 谎报 99（元素一个不少），宿主 `size() < 100` 成立后走正常分支，
方法返回后立即换回真实列表。这期间宿主只做「弹对话框 / 跳新增页 + notifyDataSetChanged」，
`size()` 读数偏小最多导致一帧少渲染几条，换回后下次刷新即恢复。

### 6.4 超长确认后保存成功提示

自实现保存复刻了宿主的「写文件成功 → 广播 `onAdd` → 管理器刷新」，但**不**弹
「添加成功」toast（宿主那个 `e(R.string.lazy_add_succ_tip)` 是私有方法，
强依赖它反而脆弱）。失败时（写文件返回 false）回落到宿主原逻辑，由宿主弹「字数超限」提示。
