# 无障碍增强 — 移植方案评估

> 评估对象：原项目 fkfluidcloud「功能六：设置 App 的无障碍增强」（`AccessibilityHook.kt`）
> 目标平台：ColorOS 17 / Android 17 / OnePlus 15（逆向素材 `E:/WorkBuddy_All/APP/oneplus`，设置 17.0.0）
> 结论先行：**原方案（hook 设置进程 `SettingsActivity#onCreate`）已是在本机约束下最优雅的方案**，
> 全部替代方案均有致命缺陷；ColorOS 17 逆向验证原 hook 点**全部成立**，按原样移植 + 三处微优化。

---

## 1. 功能定义

当某个 App 主动跳转到系统「无障碍设置页」时，模块替用户完成「给这个 App 开无障碍」的操作，共四项开关：

| 开关 | 行为 |
|---|---|
| 直接授权无障碍服务 | 把来源 App 的无障碍服务写进 `ENABLED_ACCESSIBILITY_SERVICES`，并置 `ACCESSIBILITY_ENABLED=1`，然后关掉设置页（一次点击到位） |
| 无障碍服务直达 | 跳过服务列表，直接打开该 App 的无障碍服务详情页（用户只需点最后一个开关） |
| 智能授权无障碍服务 | 白名单内的 App 自动授权；白名单外的走「直达」 |
| 自动重启服务 | （配合上面任一项）授权时先移除再重新添加该服务，迫使系统重启它 |

全部关闭时模块不做任何事，行为与原生完全一致（默认态）。

## 2. 原项目实现分析

### 2.1 核心约束：为什么必须 hook 设置 App

写 `Settings.Secure.ENABLED_ACCESSIBILITY_SERVICES` 需要 **`WRITE_SECURE_SETTINGS`**（`signature|privileged` 级权限）：

- 设置 App 的清单里带着它（逆向验证：设置 17.0.0 manifest 第 75 行 `<uses-permission android:name="android.permission.WRITE_SECURE_SETTINGS"/>`）；
- 普通 App（包括被授权的那个 App、包括模块 App 自身）拿不到；
- `pm grant` 对 signature 级权限抛 `SecurityException: not a changeable permission type`，root 下也授不了。

所以「自动授权」只能**在设置进程里**执行 —— 这就是宿主必须是 `com.android.settings` 的原因。

### 2.2 Hook 点与触发链

```
用户操作 App X（如某自动化工具点「去开启」）
  → X startActivity(ACTION_ACCESSIBILITY_SETTINGS)
  → 系统跨应用启动时自动填 referrer（android-app://<X包名>）
  → 设置进程创建 Settings$AccessibilitySettingsActivity（extends SettingsActivity，未覆写 onCreate）
  → 【Hook 点】SettingsActivity#onCreate(Bundle).proceed() 之后
  → 读 intent.action == ACCESSIBILITY_SETTINGS && referrer.host == X
  → AccessibilityManager.installedAccessibilityServiceList 里找 X 声明的服务类名
  → 按开关分流：authorize()（写 Secure + finish）或 jumpToDetails()（startActivity 详情页）
```

### 2.3 两个关键细节（原实现已处理）

1. **必须同时写 `ACCESSIBILITY_ENABLED=1`**：`AccessibilityManagerService` 只在总开关为 1 时才真正启用列表里的服务；漏写会在「无障碍总开关本来是关的」时静默失败。
2. **「直达」走 `Settings$AccessibilityDetailsSettingsActivity`**（设置清单里导出、带 `OPEN_ACCESSIBILITY_DETAILS_SETTINGS` 权限），它内部读 `android.intent.extra.COMPONENT_NAME` 并按服务类型选正确 Fragment —— 不用猜 Fragment 类名，宿主换版本不失效。

## 3. ColorOS 17 逆向验证结论（设置 17.0.0，已逐项实证）

| 验证项 | 结果 | 证据 |
|---|---|---|
| `com.android.settings.SettingsActivity` 存在 | ✅ | `decompiled/settings/sources/com/android/settings/SettingsActivity.java` |
| `SettingsActivity#onCreate(Bundle)` 签名 | ✅ | 第 720 行 `public void onCreate(Bundle bundle)` |
| `Settings$AccessibilitySettingsActivity extends SettingsActivity` | ✅ | `Settings.java` 第 74 行，**未覆写 onCreate**（挂基类必被调用） |
| manifest 中 `ACCESSIBILITY_SETTINGS` 的处理者 | ✅ | manifest 第 3204 行正是该类（Fragment = `OplusAccessibilitySettings`，ColorOS 私有类名，但 hook 在 Activity 上，无影响） |
| `Settings$AccessibilityDetailsSettingsActivity` 存在 | ✅ | `Settings.java` 第 64 行；manifest 第 3216 行，权限 `OPEN_ACCESSIBILITY_DETAILS_SETTINGS` |
| 详情页读 `android.intent.extra.COMPONENT_NAME` | ✅ | `AccessibilityDetailsSettingsFragment.java` 第 147 行 `getActivity().getIntent().getStringExtra("android.intent.extra.COMPONENT_NAME")` |
| 设置 App 持有 `WRITE_SECURE_SETTINGS` | ✅ | manifest 第 75 行 |

**附加频率评估**：`SubSettings extends SettingsActivity` 且未覆写 `onCreate`（`SubSettings.java` 第 12 行）⇒ 设置里**每个子页**打开都会触发本钩子。但见 §5 量化：单次开销纳秒级，总量可忽略。

## 4. 替代方案评估（回应「更优雅 / 性能影响更小」）

| 方案 | 做法 | 评估 | 结论 |
|---|---|---|---|
| **A（原方案）** | hook 设置进程 `SettingsActivity#onCreate`，action + referrer 过滤 | 触发点就是「用户跳到无障碍页」这一刻，来源包名由系统免费提供；设置进程天然有写权限；全 `runCatching` 容错，失败只放行 | ✅ **采用** |
| B | 模块 App 自身写 Secure settings | 模块 App 无 `WRITE_SECURE_SETTINGS`，`pm grant` 对 signature 权限无效；即使用 root 强授也依赖用户手动 adb，违背纯 hook 定位 | ❌ 权限不可得 |
| C | root shell `settings put secure ...` | 设备有 root，但：每次授权起一个 su 进程（数百 ms）；「自动重启」的移除-重加间隔时序在 shell 里难控；模块目前零 root 依赖，引入 su 后无 root 设备直接失效 | ❌ 更重更脆 |
| D | hook system_server 的 `AccessibilityManagerService` | 写权限有，但**没有自然触发点**——AMS 不知道「用户想给哪个 App 开无障碍」，仍需从设置页拿 referrer，绕回方案 A；且 system_server 作用域成本更高（改动要重启手机才生效，设置进程热重载即生效） | ❌ 触发点缺失 |
| E | hook 被授权的 App 自身 | 同样缺 `WRITE_SECURE_SETTINGS` | ❌ 权限不可得 |
| F | 改 hook 无障碍页 Fragment（`OplusAccessibilitySettings`） | 比 Activity 基类「窄」，但：ColorOS 私有类名，换版本/混淆即失效（而方案 A 的 action 过滤与版本无关，自校验）；fragment 的 `onCreateView` 等是布局路径；省下的开销仅 3 次内存读 + 1 次字符串比较（纳秒级） | ❌ 收益为零、脆弱性大增 |

**结论：不存在比原方案更优雅的替代路径。** 原方案恰恰是「用最小的注入面（1 个进程、1 个方法、1 次早退）办成必须系统权限才能办的事」。

## 5. 性能影响量化

钩子体在每次 `SettingsActivity`/`SubSettings` 创建时执行：

```
proceed() → 3 次 SharedPreferences 内存读（getBoolean）→ 1 次 intent.action 字符串比较 → 早退
```

- 触发频率：用户手动导航设置页的节奏（一次会话最多几十次），**不是帧循环/渲染热路径**；
- 单次开销：SP 读 = 内存 map 查表（无 IO、无锁），字符串比较 = 指针比较优先，合计**纳秒级**；
- 默认态（四开关全关）即早退，功能未启用时与不装钩子无实质差别；
- 唯一一次真实工作量发生在「用户主动跳无障碍页」这一刻：一次列表查询 + 一次 Secure 写入，本就是用户期待的操作，不构成额外负担。

对比参照：流体云 hook 挂在 metis 的卡片渲染/识别路径（每次内容解析都跑），那才是需要谨慎的热路径；本功能的触发频率低两个数量级以上。

**可做的微优化（移植时落实）**：

1. 钩子体内**先查 intent.action 再查开关**（action 检查更便宜，让 99% 的调用少走 3 次 SP 读）；
2. 白名单读取天然短路（`a11yAutoAuth && (pkg in whitelist)`，Kotlin `&&` 从左到右短路，不开智能授权就不读白名单）；
3. 安装时类/方法找不到只记一行 W 日志并跳过（版本自适应），绝不影响设置页。

## 6. 移植落点设计（对 ColorOSTools 的改造面）

### 6.1 hook 侧

| 文件 | 改动 |
|---|---|
| `hook/HookEnv.kt` | 新增常量 `PKG_SETTINGS = "com.android.settings"` |
| `hook/MainHook.kt` | `installForPackage` 增加 settings 分发分支（`pkg == HookEnv.PKG_SETTINGS` → `AccessibilityEnhanceHook.install()`） |
| `hook/hookers/AccessibilityEnhanceHook.kt` | **新增**。移植自 `AccessibilityHook.kt`：`SettingsActivity#onCreate` 后置钩子 + action/referrer 过滤 + 四开关分流；反射走 `ref/Reflect.kt`，日志走 `utils/LogUtils.kt`，开关读 `HookEnv.settingBoolean/settingString`（与 App 侧 `SettingsPrefs` 同源，无需额外同步通道） |
| `resources/META-INF/xposed/scope.list` | 增加 `com.android.settings`（注释记录依据） |

配置键（App 侧 `SettingsPrefs` 写入，hook 侧同键读取，5 个）：

| 键 | 类型 | 默认 |
|---|---|---|
| `a11y_direct_auth` | bool | false |
| `a11y_jump` | bool | false |
| `a11y_auto_auth` | bool | false |
| `a11y_restart_service` | bool | false |
| `a11y_auto_auth_whitelist` | string（逗号分隔包名） | "" |

（键名与上游 fkfluidcloud 保持一致，便于对照溯源。）

### 6.2 UI 侧

| 文件 | 改动 |
|---|---|
| `ui/compose/scopes/apps/AccessibilityEnhancePage.kt` | **新增**。对齐流体云页面范式：L2 页（四开关 + 白名单入口）+ L3 页（白名单应用选择，只列有启动图标的 App，带搜索） |
| `ui/compose/scopes/ScopePageRegistry.kt` | `init` 注册、`treeOrder` 加 `android_settings`、`pageTargetMap` 自映射 |
| `res/values/strings.xml` + `values-zh-rCN/` | 中英文文案（页标题、4 开关标题/摘要、白名单页） |

### 6.3 生效性与回滚

- 设置 App 是长驻进程但会被系统杀掉重启 ⇒ 开关改完后「重启设置」或等其自然重建即生效，无需重启手机；
- 钩子安装失败/类不存在只记日志，设置页行为完全不受影响；
- 回滚成本 = 删一个 Hooker 文件 + 删两个 UI 文件 + 撤 3 处注册 + scope.list 去掉一行，与流体云功能完全解耦。

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| ColorOS 未来版本改类名/混淆 | 安装时按类存在性自适应（类不存在只记 W 日志）；「直达」走设置自己的 `AccessibilityDetailsSettingsActivity` 入口，不猜 Fragment 类名 |
| referrer 拿不到（系统改行为/从设置内部打开） | 记 W 日志后放行，行为退化为原生 |
| 写 Secure 失败（权限被收） | `runCatching` 包裹，记 E 日志后放行，设置页不崩 |
| 误伤设置自身/桌面打开的无障碍页 | referrer host == 设置包名或以 launcher 开头时跳过（原实现已有） |
| 「自动重启」两次写入被 AMS 合并 | 原实现用 600ms 间隔 + 先读后写，移植时保留 |
