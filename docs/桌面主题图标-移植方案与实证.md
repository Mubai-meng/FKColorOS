# 通知图标跟随桌面主题图标 —— 方案对比、移植与实证

> 日期：2026-11-24　版本：1.5.13（184）
> 宿主：`com.android.systemui`（System UI 17.99.02）
> 参考实现：`Mubai-meng/Glyph`（`com.fankes.coloros.notify`，YukiHook 1.5.0）
> 适配资源：`E:\WorkBuddy_All\APP\fanbianyi\系统界面_17.99.02`

## 1. 要做的事

桌面上的 App 图标不是 APK 里的 `ic_launcher`，而是 ColorOS 主题引擎渲染出来的（主题图标包 / 用户自定义图标 / 花式图标）。本功能让**状态栏与悬浮通知的图标改用桌面当前那一张**，与桌面视觉统一。

开关落位：「系统界面」功能页（`pageKey = lock_screen`）。

---

## 2. 取图链路（唯一入口，无法绕开）

```text
android.app.UxIconPackageManagerExt            ← framework 隐藏类
  ├─ loadItemIcon(PackageItemInfo, ApplicationInfo, boolean): Drawable
  └─ loadItemIconWithoutEdit(...)              ← 4 参 private 的 public 包装
        └─ OplusThemeManager#getDrawableFromUxIcon
              └─ OplusUXIconLoadHelper#getDrawable
                    └─ OplusUXIconLoaderImpl#loadUxIcon
                          ├─ isThemeIconPack() ⇒ OplusIconPackDelegate
                          └─ else ⇒ mCurrentStyleForTheme.tryLoadThemeIcon
```

`loadItemIcon` 内部优先级：花式图标 → 用户自定义图标（`/data/oplus/uxicons/choose/<pkg>.png`，联系人特判 `dialer_<pkg>.png`）→ 主题图标包 / 当前主题样式 → APK 原始 `ic_launcher`。

**结论：调一次 `loadItemIcon` 就同时覆盖「主题图标」与「自定义图标」两种情况**，不需要自己判断主题模式（矩形/圆形/暗色补偿都在 ColorOS 内部）。

⚠️ 第一个参数必须传 **`ActivityInfo`**（桌面按 activity 维度套图标），传 `ApplicationInfo` 会与桌面显示不一致。取法：`LauncherApps#getActivityList(pkg, user)` → `PackageManager#getActivityInfo(componentName, 0)`，失败才回退 `getApplicationInfo`。

⚠️ Android 17 已移除 `getActivityInfoAsUser`，不要探测。`StatusBarNotification#getUserId()` 在无显式用户时返回 `USER_NULL(-1)`，查 -1 必定 `NameNotFoundException` ⇒ 先归一化到主用户。

## 3. 挂载点：三方案对比

SystemUI 里图标数据流有**三个互不共用的出口**：

| 出口 | 取图代码 | 覆盖面 |
|---|---|---|
| A 状态栏 / 悬浮通知 / AOD 通知 / 锁屏状态栏 | `StatusBarIconView#getIcon(StatusBarIcon)` | 最大 |
| B 通知面板头部行 | `CachingIconView` + `Notification.getSmallIcon().loadDrawable(ctx)`（`OplusNotificationHeaderViewWrapperExImp#getBadge`） | 面板内 |
| C 锁屏胶囊 | `CapsuleNotificationDataController` → `icon.loadDrawable(ctx)` | 锁屏 |

### 方案 A：Glyph 原式 —— 挂 `IconManager#getIconDescriptor(NotificationEntry, boolean)`

```java
// IconManager.java L185
public final StatusBarIcon getIconDescriptor(NotificationEntry e, boolean z) {
    StatusBarIcon avatar = e.getIcons().getPeopleAvatarDescriptor();
    StatusBarIcon small  = e.getIcons().getSmallIconDescriptor();
    if (avatar != null) return avatar;        // ← 命中缓存直接 return
    ...
    e.getIcons().setSmallIconDescriptor(statusBarIcon);
}
```

**缺点三条：**

1. 方法开头命中 `IconPack.mSmallIconDescriptor` 就 early-return ⇒ **每次通知刷新不一定重走**，覆盖面受限；
2. 返回的是 `StatusBarIcon`，要 `cloneStatusBarIcon` 再塞回 `preloadedIcon` + `icon`，实参搬运容易出错；
3. 后面还有 `StatusBarIconView#set(StatusBarIcon)` 的 Icon 判等（按 type/resPackage/resId），**相等就跳过 `updateDrawable`** —— 换了 Icon 但 resId 没变时静默失效。

### 方案 B（采用）：挂 `StatusBarIconView#getIcon(StatusBarIcon)`

```java
// StatusBarIconView.java L251，public final，method_idx 28204（classes2.dex）
public final Drawable getIcon(StatusBarIcon statusBarIcon) {
    Drawable drawable = statusBarIcon.preloadedIcon;
    if (drawable != null) { ... constantState.newDrawable(res).mutate() ... }
    else { ... statusBarIcon.icon.loadDrawableAsUser(context, identifier) ... }
    ... DrawableSize.downscaleToSize(res, dr, preference_item_padding_inner, ...) ...
}
```

选它的理由：

- **无缓存短路**：`updateDrawable(boolean)` 每次都调它（L794），而 `updateDrawable` 是 `set()` / `updateIconDimens()` / 图标等级变化的总出口；
- **返回什么就显示什么**：我们直接返回 `BitmapDrawable`，不需要克隆 `StatusBarIcon`、不触发 `set()` 的 Icon 判等；
- **一处覆盖 A 出口全部场景**（状态栏、悬浮、AOD、锁屏状态栏都是同一个 View 类）。

### 方案 C：改 `notification.extras` 塞 `oplus_smallicon_use_app_icon = true`

ColorOS 原生就有一个「用应用图标」标志（framework `Notification.oplus_smallicon_use_app_iconP_ICON`）：

```java
// StatusBarIconControllerExImpl L171
boolean z = !OplusNotificationSmallIconUtil.useAppIconForSmallIcon(n)
        && OplusContrastColorUtil.getInstance(ctx).isGrayscaleIcon(drawable);
view.setTag(R.id.icon_is_grayscale, z);
view.setIsIconColorable(z);
```

看到 `useAppIconForSmallIcon` 就知道：塞这个 extras 会让原生自己算出 `isColorable = false`，确实优雅。**但它不解决「换哪张图」**——它只是让宿主别再给图标套单色遮罩，图标本身还是通知的 `smallIcon`。所以它不能单独成方案，只能作为**方案 B 的着色补充**。

而且直接写 extras 有副作用：`OplusNotificationHeaderViewWrapperExImp` 的 L765 / L1324 与 `CapsuleNotificationDataController` L1832 都按这个标志切分支，会连带改面板/胶囊的徽标渲染。风险大于收益。

**最终着色处理**：见下节，另挂 `updateStatusBarIconGrayScale` 做定点修正，不碰 extras。

### 覆盖边界（明确不做的部分）

B、C 两个出口需要额外钩子，且都要处理 Kotlin 协程续体（`getBadge(ContinuationImpl)`）或状态机，Glyph 为此写了 `NotificationPanelHooks`(371 行) + `LockScreenCapsuleHooks`(377 行) + `AodNotificationHooks`(175 行) + `FullScreenBannerHooks`(238 行)。本轮**只做 A 出口**，理由是视觉面积小、属于「通知详情」语境，与风险不成正比。后续要补各自单列 Hooker 即可（方案已定，缺的只是协程钩子）。

## 4. 着色：全彩图标不能被当单色遮罩处理

`StatusBarIconView` 默认 `mIsIconColorable = true`（构造器 L183），此时 `updateIconColor$1()` 会按通知前景色打 `ColorMatrixColorFilter` —— 全彩桌面图标被染一遍就成了白块。

ColorOS 的判定靠**猜像素**（`OplusImageUtils#isGrayscale`：缩到 64×64、每 3 个像素取 1 个、要求 `abs(R-G)<25 && abs(R-B)<25 && abs(G-B)<25`）。多数主题图标是全彩的，猜得对；**单色图标包**会被猜成灰阶 ⇒ 又被染色。

所以再挂一个 `updateStatusBarIconGrayScale(Drawable, StatusBarIconView, StatusBarNotification): void`：**只要这条通知确实换成了主题图标**（`DesktopThemeIconProvider.isResolved(pkg, userId)`），就

```kotlin
Reflect.callDeep(view, "setIsIconColorable", false)   // 清颜色滤镜
view.setTag(R.id.icon_is_grayscale, false)            // 面板侧会读这个 tag
```

这与 ColorOS 自己「用了应用图标就别再染色」的语义完全对齐（原生就是 `useAppIconForSmallIcon == true` 时判 false）。

---

## 5. 尺寸：scaleType = CENTER，位图多大就显示多大

`StatusBarIconView` 构造器 L191 `setScaleType(ImageView.ScaleType.CENTER)` —— **不缩放**，只有 `StatusBarIcon.Shape.FIXED_SPACE` 才临时换 `FIT_CENTER`。所以位图比 View 大就被裁、小就显小。

本项目直接返回自己的 Drawable，**跳过了原方法末尾的 `DrawableSize.downscaleToSize(...)`**，因此必须自己按 View 尺寸渲染：

1. 优先 `max(view.width, view.height)`；
2. 首帧 `getIcon` 早于布局、宽高为 0 ⇒ 回退宿主 `status_bar_icon_size` dimen（17.99.02 = 20dp）；
3. 再兜底 `android.R.dimen.app_icon_size`，最后写死 72px，统一夹在 48..192 px。

位图化两步：先整块渲染，再**裁掉四周全透明区域**（桌面图标自带约 1/6 自适应边距），按 `CONTENT_RATIO = 0.9` 居中铺回 —— 留 5% 单边边距，视觉上才和旁边的信号/WiFi 图标齐平。

## 6. 关掉开关必须能恢复（`preloadedIcon` 污染）

`StatusBarIconView#updateDrawable` 会把 `getIcon()` 的返回值缓存进 `StatusBarIcon#preloadedIcon`：

```java
StatusBarIcon statusBarIcon = this.mIcon;
if (statusBarIcon.preloadedIcon == null) statusBarIcon.preloadedIcon = icon;
```

即**我们返回的主题图标会被写进宿主状态**。之后 `getIcon` 走 `preloadedIcon != null` 分支、不再重新取图 ⇒ 关掉开关后图标会一直停在主题图标上，只有重启 SystemUI 才恢复。

所以：

1. 本模块返回的是私有子类 `ThemeIconDrawable : BitmapDrawable`（只为能识别「这是我们写的」——用 `is BitmapDrawable` 判定不行，原生 `preloadedIcon` 本身通常就是 `BitmapDrawable`）；
2. 开关关闭时，先把 `preloadedIcon` 里那个 `ThemeIconDrawable` 置 null，再 `proceed()`，原方法自然会走 `icon.loadDrawableAsUser(...)` 重新取原生图标。

## 7. 缓存

`getIcon` 是「每条通知每次刷新都走」的热路径。三层：

| 层 | 键 | 失效方式 |
|---|---|---|
| 配置快照 | — | 300ms TTL（含 `mThemeChanged` / `mThemeChangedFlags` / `mUxIconConfig` / `uiMode`） |
| 位图 LRU（4MiB） | 包名 + 用户 + 尺寸 + 配置快照 | 键含快照 ⇒ 换主题即失效，**不需要 TTL** |
| 失败 LRU（256） | 同上 | 同上（**必须缓存 miss**，否则每次刷新都重跑全套反射） |

## 9. 验证要点（真机）

1. 打开「系统界面 → 通知图标跟随桌面主题」，重启 System UI（页面已带重启开关）；
2. 发一条通知（微信/QQ 等有主题图标的应用）：状态栏图标应为**桌面那张全彩图标**，不是单色遮罩版；
3. 换一套图标风格（主题商店换主题图标包）→ 通知重新下发后图标应跟着变；
4. LSPosed 日志过滤 `DesktopThemeIcon`：
   - `主题图标接口就绪：loadItemIcon=true ...` ⇒ 反射链打通；
   - `已用桌面主题图标替换状态栏图标（首个命中：xxx）` ⇒ 替换生效；
   - 若出现 `未找到 android.app.UxIconPackageManagerExt` ⇒ 该 ROM 没有此扩展，功能自动静默降级（保留原图标，无副作用）。

### 已知限制

- **换主题后已存在的通知不会立刻变** —— `StatusBarIconView#set()` 只在 `Icon` 变化时才重绘。需要等该通知下一次更新，或重启 System UI。（参考实现靠 `NotificationRefreshBridge` 主动触发刷新，本轮未移植。）
- 通知面板下拉后的头部行、锁屏胶囊**未覆盖**（见 §3 覆盖边界）。

## 附：v1.5.14 二次返工（2026-11-24 晚）

### 1. 为什么第一版"状态栏也没变"

用户反馈"状态栏那个也没有跟随主题图标，形状不一样的"。从 LSPosed 日志导出包里查到的决定性证据：

```
grep "(com.android.systemui)\[com.fr.colorostools" log/*.log   → 0 条
grep "(system)[com.fr.colorostools"               log/*.log   → 712 条
```

即 **模块只注入进 system_server，从未注入 SystemUI**。而 `modules_state.enabled=1`、
`scope` 含 `com.android.systemui`、`apk_path` 有效、`enable_log=1`、`desktop_theme_icon_enabled=1`
全部正常。SystemUI 进程 pid 6232 自 19:28:48 启动后一直没重启 —— **LSPosed 只在 zygote fork
时决定注入哪些模块，作用域勾选/新版 APK 晚于进程启动就一定要重启该进程**。

> 排查铁律：遇到"模块零日志零效果"，先 grep `(目标进程)[模块包名`，不要先怀疑代码。

### 2. 为什么第一版覆盖不全

SystemUI 17.99.02 里「通知小图标」有**四条互不相交**的取图路径：

| 界面 | 取图路径 |
|---|---|
| 状态栏 / 悬浮通知 / AOD 状态栏 | `IconManager#getIconDescriptor` → `StatusBarIconView#getIcon` |
| 通知面板下拉的头部行 | `OplusNotificationHeaderViewWrapperExImp#getBadge` → `getSmallIcon().loadDrawable()` |
| 锁屏通知卡片 / 胶囊 | `CapsuleNotificationDataController` → `icon.loadDrawable()` |

第一版只挂了第一条，所以锁屏和通知列表纹丝不动（正是用户截图指出的地方）。

### 3. 补齐：源头通道

新增 `NotificationListener#onNotificationPosted(StatusBarNotification, RankingMap)`（public final）钩子，
在 `chain.proceed()` **之前**把 `Notification#smallIcon` 换成主题图标位图 —— 下游所有路径读的都是这个字段，
一处全覆盖。原 `StatusBarIconView#getIcon` 通道保留，负责状态栏的精确尺寸渲染。

两个实现细节：

- `Notification#smallIcon` 是 public **字段**，但 Kotlin 见到 `getSmallIcon()` 会把它合成为只读属性，
  直接赋值报 `'val' cannot be reassigned` ⇒ 必须 `notification.javaClass.getField("smallIcon").set(...)`；
- 同时写 `extras["oplus_smallicon_use_app_icon"] = true`（framework `Notification.OPLUS_SMALLICON_USE_APP_ICON`），
  让 `updateStatusBarIconGrayScale` 的判据 `!useAppIconForSmallIcon(n) && isGrayscaleIcon(d)` 直接得 false，
  不再靠猜像素决定是否套单色遮罩。

### 4. 日志可见性

`MainHook` 的「系统界面宿主命中」与 `DesktopThemeIconHook.install()` 的安装结果改用 `LogUtils.e` ——
即使「详细日志」开关关闭也能在 LSPosed 日志里看到，这是确认「模块有没有进 SystemUI」最快的锚点。

## 附：v1.5.15 三次返工 —— 真正的根因 `ActivityInfo.icon == 0`

### 定位过程

第三次 LSPosed 日志（`LSPosed_20261124_205854.zip`，用户手动重启后）显示模块**这次确实注入进 SystemUI 了**：

```
(com.android.systemui)[com.fr.colorostools   → 20 条
DesktopThemeIcon: install -> 已挂 NotificationListener#onNotificationPosted
DesktopThemeIcon: install -> 已挂 StatusBarIconView#getIcon
DesktopThemeIcon: install -> 已挂 StatusBarIconControllerExImpl#updateStatusBarIconGrayScale
DesktopThemeIcon: install -> 主题图标接口就绪：loadItemIcon=true loadItemIconWithoutEdit=false
DesktopThemeIcon: getIcon -> 已用桌面主题图标替换状态栏图标（首个命中：com.android.systemui）
```

钩子全装上了、开关读到 true、接口句柄也拿到了，**但只有 `com.android.systemui` 一个包命中**，
第三方包（微信等）全部 miss，源头通道零命中。

### 根因

`OplusUXIconLoaderImpl#loadUxIcon`（oplus-framework）：

```java
if (resId == 0 && !isThemeIconPack()) {
    IconDebugUtils.getIconEvent().handled("LOAD_UX_ICON_FAILED: resId is 0");
    return null;            // ← 直接放弃，连 APK 原始图标都不回退
}
```

`resId` 就是传进去的 `itemInfo.icon`。而 `PackageManager#getActivityInfo` 返回的
**`ActivityInfo.icon` 对绝大多数应用是 0** —— 图标写在 `<application android:icon>` 上，
activity 自己不声明。于是：

- 有启动 activity 的包（微信、QQ……恰好是用户真正看通知的那些）→ `ActivityInfo.icon == 0`
  → `loadUxIcon` 返回 null → `loadItemIconWithoutEdit` 返回 null
  → `UxIconPackageManagerExt#loadItemIcon` **对返回值不做 null 兜底**，一路 null 给我们；
- 没有启动 activity 的包（SystemUI 自己）→ `LauncherApps#getActivityList` 空
  → `itemInfo` 回退 `ApplicationInfo`（`icon` 有效）→ 成功。

**这正好解释「唯一的命中的是 com.android.systemui」这个反常现象。**

### 修法

`DesktopThemeIconProvider#resolveItemInfo`：

1. `appInfo` 统一用 `pm.getApplicationInfo(pkg, 0)`（不再信任 `LauncherActivityInfo#getApplicationInfo`
   的完整性）；
2. 启动 activity 优先 `LauncherActivityInfo#getActivityInfo()`（`LauncherApps` 生成，icon 已填充），
   次选 `pm.getActivityInfo(componentName, 0)`；
3. **`if (item.icon == 0) item.icon = appInfo.icon`** —— 关键的一行。`activityName` 保留，
   所以「按 activity 维度套主题图标」的语义不丢。

### 同时修掉的两个隐患

- **失败缓存从「永久」改成 8 秒 TTL**：冷启动头几秒 `LauncherApps` / `PackageManager` 可能还没就绪，
  那时的失败是暂时的；永久缓存会让功能整个运行期都不重试。这是第二可能的杀手。
- **`getIcon` 命中时顺手改 `notification.smallIcon`**：存量通知不会再走 `onNotificationPosted`
  （`NotificationListener#onListenerConnected` 对 `getActiveNotifications()` 是直接分发给
  handler，不经过该回调），面板头部行 / 锁屏卡片读的是 `getSmallIcon()`
  ⇒ 在状态栏取图时补写一次源字段，才能让那两处也吃到新图。

### 新增启动自检（下次抓日志可直接定位）

`install()` 后延迟 4 秒，对 `com.android.systemui` / `com.tencent.mm` 各跑一遍完整链路，
逐段打 ERROR 级日志：

```
DesktopThemeIcon: diagnose -> [com.tencent.mm] ① 反射句柄 api=true loadItemIcon=true
DesktopThemeIcon: diagnose -> [com.tencent.mm] ② appInfo=true appIcon=2131034112
DesktopThemeIcon: diagnose -> [com.tencent.mm] ③ launcherActivities=1 item=ActivityInfo itemIcon=2131034112 activityName=...
DesktopThemeIcon: diagnose -> [com.tencent.mm] ④ loadItemIcon -> AdaptiveIconDrawable intrinsic=...
DesktopThemeIcon: diagnose -> [com.tencent.mm] ⑤ resolve -> 144x144
```

哪一步变 null 就是故障所在。另外 `getIcon` / `onPosted` 各自前 8 次调用都会记录
`包名 -> 命中/未取到`，不再只有「首个命中」一条而看不到后续。

### A. 热路径（每条通知每次刷新都会走）

| # | 问题 | 改动 | 省掉什么 |

| 1 | `getIcon` 原来**总是先 `chain.proceed()`** 再判断要不要换图 | 改成「先算我们的图，拿到就 return，不调原方法」 | 宿主每次的 `icon.loadDrawableAsUser()` 解码 + `getValue(scale_factor)` + `getDimensionPixelSize()` + `DrawableSize#downscaleToSize()`（后者**新分配一块目标尺寸位图并整块 draw**）。状态栏刷新有多频繁就白做多少次 |
| 2 | `patchSmallIcon` 每次 `getIcon` 都 `Icon.createWithBitmap` + 反射写字段 | 加幂等短路：`notification.smallIcon` 已是同一 `Bitmap` 实例就直接返回 | 一次 `Icon` 分配 + 一次反射写 + 下游 `IconManager` 的重复解析/重绘 |
| 3 | `Icon#getBitmap()`（@hide）与 `Notification#setSmallIcon(Icon)` 的 `Method` 每次重找 | 句柄 `@Volatile` 缓存（含「宿主没有」的哨兵） | ART 上 `getMethod` = native 查找 + 克隆 Method，**未命中还要构造并填栈异常** |
| 4 | `applyHeaderIcon` 的 `mRow` 反射取值放在短路**之前** | 挪到短路未命中之后 | `updateIconColor` 每次颜色重算都会进这条路径，短路命中时白做一次字段查表 |
| 5 | `applyRowIcons` 用**同一个 Drawable 实例**铺到多个 View | 每个 View 各自 `new ThemeIconDrawable`（位图仍共享，零额外内存） | 修掉「宿主给各视图分别打滤镜 ⇒ 互相污染」；与 `applyHeaderIcon` 的做法对齐 |

|---|---|---|---|
| 7 | `resolveItemInfo` 没缓存 `(PackageItemInfo, ApplicationInfo)` | 加 `itemInfoCache`（LRU 128，TTL 60s） | **换主题时位图键全变 ⇒ 每个通知包各两次跨进程 binder**（`getApplicationInfo` + `LauncherApps#getActivityList`）的续航尖峰。TTL 是为了包升级/卸载后自愈 |

### C. 修掉的功能 bug（不是性能问题，但同属「全量检查」发现）

**图标一直偏小 / 首帧尺寸永久固化。** `StatusBarIconView#updateDrawable(boolean)` L787：
```java
if (preloadedIcon == null) preloadedIcon = icon;   // ⇒ 一旦写入永不刷新
```
首帧（`getIcon` 早于布局，`view.width == 0`）`iconSizePx` 回退 `status_bar_icon_size`（20dp），
这张小图被写进 `preloadedIcon` 后**此后永远不会更新**。

修法两半：① 短路条件里**连尺寸一起比对**（`pre.bitmap?.width == size`），尺寸不符就不短路、重新取图；
② 主路径把新图**主动回写** `preloadedIcon`。

### D. 复核后**确认不改**的两处（避免过度设计）

- `FluidCloudConfig.installCardBlockEnabled()` 是纯布尔直读 remote prefs（内存读，无 IPC），
  叠加 TTL 只会让「关开关后仍拦几张卡」，收益为零 —— 不加。
- `Reflect.findMethodByShape` 不走缓存，但**全部调用点都在 install 阶段**（每进程一次），
  挪进热路径才需要缓存 —— 不动。

### 定论：锁屏卡片的图标控件是 `NotificationRowIconView`，不是 `CachingIconView`

内置诊断打出的窗口视图清单（节选）：

```

    父=FrameLayout<NotificationContentView<ExpandableNotificationRow
```

三点结论：

1. 锁屏/面板用的是 ColorOS「2025 hybrid」布局，图标控件为

   `ExpandableNotificationRow` 树上的**同一棵树**，所以按行重铺（`setOnKeyguard`）就能覆盖；
