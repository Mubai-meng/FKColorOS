# 输入法面板透明模糊限制 — 定位与 Hook 方案分析

> 宿主：百度输入法定制版 `com.baidu.input_oppo`（ColorOS 17 / OnePlus 15 / Android 17 / API 37）
> 素材：`E:/WorkBuddy_All/APP/oneplus/decompiled/baiduime`（jadx 反编译）
> 参照：LuckyTool `hook/scopes/opluskeyboard/ForceEnableOplusKeyboardBlur.kt`（expressive 分支，针对小布输入法）
> 结论一句话：**限制是宿主内置的「客户端白名单」，不是系统强制；最小侵入点是 hook 白名单判定方法 `ep0.l.g()` 恒返回 true，其余判据全部保留。**

---

## 1. 现象与结论

| 场景 | 前台应用 | 面板表现 |
|---|---|---|
| 图二（有模糊） | `com.heytap.market` 软件商店 | 键盘背景半透明 + 背景内容高斯模糊 |
| 图一（无模糊） | 抖音（第三方） | 键盘背景纯色不透明（`#ffffffff` 浅色 / `#ff1e1e1e` 深色） |

差异与皮肤无关（同一默认皮肤），与输入法自身能力无关，而是宿主在每次输入目标切换时做的一次「是否允许模糊」判定。

## 2. 模糊完整链路（数据流）

```
键盘面板 View
  └─ ep0.e.a(view, cornerRadius, BlurColorParam)          # 宿主模糊工厂（唯一汇聚点）
       ├─ new com.oplus.view.ViewRootManager(view)        # 框架类，不受宿主混淆影响
       │    └─ view.getViewRootImpl().createBackgroundBlurDrawable()
       │         └─ com.android.internal.graphics.drawable.BackgroundBlurDrawable
       │              ├─ setBlurRadius(150=DARK / 50=LIGHT)
       │              └─ setBlurParams(OplusBlurParam{blurType=2=FAST_KAWASE, materialParams})
       └─ view.setBackground(blurDrawable)
                 │
                 ▼
       ViewRootImpl.dispatchBlurRegions(float[][] , frameNumber)
         └─ SurfaceControl.Transaction.setBlurRegions(surfaceControl, regionCopy)
                 │
                 ▼
       SurfaceFlinger（Kawase 后处理，模糊该 surface 下方内容）
```

关键事实：

1. 模糊不是输入法自己截屏/自绘，而是走 **框架 `BackgroundBlurDrawable` → SurfaceFlinger `blurRegions`** 的硬件通路（SurfaceFlinger 二进制内可见 `BlurAlgorithm`/`BlurDualFilterV`/`blur_kawase` 等符号）。
2. `com.oplus.view.ViewRootManager` 属于 **oplus-framework**（bootclasspath），类名与方法名稳定，不受宿主混淆影响 —— 这是跨 ROM 版本最稳的锚点。
3. 该通路与前台应用无关，技术上第三方应用完全可用。

## 4. 与 LuckyTool 方案的对照

| 维度 | LuckyTool（小布输入法） | 本项目（百度输入法定制版） |
|---|---|---|
| 限制形态 | 白名单 + 系统开关 + 折叠屏 + 版本号 + 默认主题 + 跟随深浅色，全部收敛到宿主总闸 `f.b()` | 白名单 + 9 项判据收敛到 `ep0.l.h()` |
| 定位手段 | DexKit 按 `key_day_night_mode` / `system_material_blur_enable` + `SettingsPrefs` 字符串特征定位混淆类 | 宿主固定 + 类名可直接反射；fallback 用结构特征（见 §5.1） |
| 主 hook 点 | 总闸类所有「无参 boolean」方法 → true；`system_material_blur_enable` 读取 → true | **只 hook `ep0.l.g()` → true**（精准放开白名单，其余判据保留） |
| 强度调节 | hook `com.oplus.view.ViewRootManager#setBlurRadius`，>0 才改写，保留 0 的关闭语义 | 同（可选，默认不改动） |
| 刻意不碰 | 折叠判断、版本号读取（风险大于收益） | 同：不碰 `h()`、不碰 SDK_INT 判断 |

**可借鉴的两点**：
1. 「总闸收敛」思路 —— 宿主把所有条件汇到一个 boolean 方法，改一处即可，不必逐个场景改渲染分支。
2. 「0 即关闭」语义保留 —— hook 半径时只拦正数请求，避免把宿主主动关闭的路径也强制打开。

**本项目更优的一点**：LuckyTool 是把总闸所有无参 boolean 全拍成 true（等价于无视系统开关/皮肤/折叠屏），我们只放开 `g()` 一项 —— 系统「质感模糊」开关关闭、非默认皮肤、锁屏、分屏、画中画、老人模式、硬键盘场景依旧不模糊，功耗行为与官方设计一致。

## 5. Hook 方案设计

### 5.1 定位策略（两级）

| 级别 | 方式 | 说明 |
|---|---|---|
| 主 | `Class.forName("ep0.l")` → `getDeclaredMethod("g")` → `XposedHelpers.findAndHookMethod` | 宿主 APK 固定，简单可靠 |
| fallback | 遍历宿主 dex 中满足以下全部特征的 static 方法：无参、返回 boolean、方法体引用 `Build.VERSION.SDK_INT`、所在类含一个 4 元素 `String[]` 静态字段且字段含 `com.heytap.market` | 宿主升级改混淆名时自愈 |

> 不使用 DexKit：本宿主白名单是硬编码 `String[]`，结构特征足够唯一且比字符串匹配更稳（`system_material_blur_enable` 在宿主内被 5 处引用，不唯一）。

### 5.2 三个 hook 点与默认策略

| # | 目标 | 动作 | 默认 | 影响面 |
|---|---|---|---|---|
| A | `ep0.l.g()` | `before` 置 `result = true` | **开启** | 仅放开白名单，9 项判据其余不动 |
| B | `ep0.l.h()` | 恒 true（备选总闸） | 关闭 | 连系统开关/皮肤/锁屏也强制模糊，功耗明显上升 |
| C | `com.oplus.view.ViewRootManager#setBlurRadius(int)` | 仅当入参 >0 且 ≠ 自定义值时改写 | 关闭（0=不启用） | 调模糊强度；半径直接决定 SF 采样开销 |

**推荐组合：只开 A。** 用户诉求是"让所有应用都有模糊"，A 已完全满足；B/C 作为进阶选项留在设置里。

### 5.3 关键代码片段（示意，libXposed API 102 原生，不用 YukiHookAPI）

```kotlin
// hook/hookers/ImePanelBlurHook.kt（object，挂 MainHook 已有 baidu.input_oppo 分发）
private const val GATE_CLASS = "ep0.l"

fun hook(loader: ClassLoader) {
    // A：放开客户端白名单（根因）
    runCatching {
        XposedHelpers.findAndHookMethod(GATE_CLASS, loader, "g", object : XC_MethodHook() {
            override fun beforeHookedMethod(param: MethodHookParam) {
                param.result = true
            }
        })
    }.onFailure { LogUtils.e("ImePanelBlur", "hook g() failed: $it") }

    // C（可选，设置开启时才挂）：自定义半径，保留 0 的关闭语义
    if (radius > 0) {
        XposedHelpers.findAndHookMethod(
            "com.oplus.view.ViewRootManager", loader, "setBlurRadius", Int::class.java,
            object : XC_MethodHook() {
                override fun beforeHookedMethod(param: MethodHookParam) {
                    val req = param.args[0] as? Int ?: return
                    if (req > 0) param.args[0] = radius
                }
            })
    }
}
```

生效时机：`he0.p.f39765x` 在 `onStartInput` 刷新，`k71/a.E()` 在输入目标/场景变化时重跑判定（`uj/j.java:244` 调用），因此 hook 后**切换应用即时生效，无需重启输入法**。

## 6. 性能影响分析（对应"尽量减小性能影响"）

### 6.1 开销本体

- 模糊由 SurfaceFlinger 的 Kawase 后处理完成（`blurType=2` = FAST_KAWASE），代价是**每帧一次模糊区域的 downsample/upsample 合成**，区域固定为键盘矩形（约 1/3 屏高）。
- ColorOS 官方已在 4 个自家应用长期开启该通路，说明硬件代价本身可接受；真正增量来自"模糊面积 × 出现频次"变多（第三方应用也会触发）。

### 6.2 本方案为何开销最小

| 措施 | 省的是什么 |
|---|---|
| 只 hook `g()`，不动 `h()` 恒 true | 系统「质感模糊」开关（`system_material_blur_enable`）关闭时、省电策略降级时依旧零模糊；非默认皮肤/锁屏/dock/pip/老人模式/硬键盘场景不引入模糊 |
| 不改 `setBlurRadius` | 维持宿主原生半径（浅色 50 / 深色 150），不主动加大采样范围 |
| hook 仅在输入法进程内执行（scope 限定 `com.baidu.input_oppo`） | 零跨进程/零系统服务改动，不碰 WMS/SF 配置 |
| 无轮询、无定时器 | 判定时机完全沿用宿主自身的 `onStartInput` / 场景变化回调 |
| 提供总开关 | 用户可在发热/掉帧时一键关闭，回退到官方行为 |

### 6.3 残余风险

1. **全应用生效后**，游戏/视频/地图等重载应用弹出输入法时会叠加模糊合成，低端机可能掉帧 —— 由设置开关兜底。
2. 宿主升级若改混淆名，主定位失效 → fallback 结构定位接住；两者都失效时打错误日志（真机可按 `OplusPanelBlur` 的 `blurDecision reason=` 快速判断是 hook 失效还是判据拦截）。
3. 不修改任何 `persist.*`、不触碰系统服务，满足项目安全纪律。

## 7. 真机验证方法（无需手动抓日志）

模块 hook 成功后，在任意第三方应用（如抖音）弹出键盘，输入法进程日志应出现：

```
OplusPanelBlur: blurDecision supported=true, reason=enabled, client=com.ss.android.ugc.aweme, ...
```

对照：未 hook 时为 `supported=false, reason=unsupportedClientOrVersion`。

辅助验证：
- `dumpsys SurfaceFlinger | grep -i blur` 确认 blur 通路使能。
- 视觉对照：第三方应用键盘背景出现与软件商店一致的半透明 + 背景模糊。

建议在 `ImePanelBlurHook` 挂接成功后主动打一条模块日志（含命中的类名/方法名），失败时打完整异常，便于回灌定位。

### 实现要点与差异（相对 §5 方案）

1. **Chain API 修正**：libxposed 102 的 `Chain` **没有** `setResult` / `setArg` —— 改结果必须 `return true`（不调 `proceed`），改参数必须 `chain.proceed(newArgs)`。
2. **半径懒安装**：`installRadiusOverride()` 只在 `settingInt(KEY_RADIUS) > 0` 时安装，0 = 不装该钩子（跟随宿主默认 50/150）。
3. **兜底定位**：主锚点 `ep0.l#g` 未命中时，扫宿主 dex（`ApplicationInfo.sourceDir` + `splitSourceDirs` → `DexFile.entries()`），按「类内含 static `String[]` 且含 `com.heytap.market`」反查白名单类，再按方法名 `g` 定位；类名按 obfuscate 形态（`^[a-z]{1,4}\.[a-z0-9]{1,4}$`）预筛，`forName` 上限 2000 次。
4. **滑块联动**：DSL 非 @Composable 上下文，不能用 `collectAsStateWithLifecycle`；改同步 `state.getBoolean`，开关写入 bump revision 触发整页重建时自然刷新。
5. **总闸链路复核（重要）**：`ep0.l#h()` 的唯一调用点是 `k71.a#E()`，其内 `dy0.e#f34003z = h()`；各渲染点（`ep0.l.a/b`、`pa.c.h`、`ai.b0`…）读的是 `f34003z` 而非 `h()`。`E()` 在 `onStartInput` 链路（`uk.e` → `k71.a.E()`）触发，故 hook `g()` 后**切换 App 即时生效**，无需重启输入法。
6. **非默认皮肤开关（v1.0.52 新增，默认关）**：hook `dy0.f#f()`，但**不做恒 true** —— 该方法在宿主内被十几处非模糊逻辑调用（AI 卡片 / 分词弹窗 / 翻译面板 / 品牌曝光 / 表情面板），恒 true 会让自定义皮肤错用默认皮肤样式。改为**调用栈过滤**：仅当 `f()` 原值为 false 且栈中存在 `ep0.l#h` 或 `k71.a#E` 帧时才返回 true，其余调用点拿真实值。
   - 副作用：`E()` 自身也读一次 `f()`（写 `f34001x`，曲面屏缩进更新用），放行后该字段与默认皮肤取值一致；`f34001x` 全宿主仅 `u00/y` 一处读取，影响可忽略。
   - 风险：若宿主把 `h()` JIT 内联进 `E()`，`ep0.l.h` 帧消失，此时靠 `k71.a.E` 帧兜住；两者都失效则开关静默无效（日志可见）。

### 真机验收清单

1. 开关开启 → 重启输入法 → 任意第三方应用（如抖音）弹出键盘：背景应变半透明 + 模糊。
2. 模块日志（App 日志页 / LSPosed 框架日志）出现 `ImePanelBlur / whitelist：已放开客户端白名单（via=static）`。
3. 宿主日志 tag `OplusPanelBlur`：`blurDecision supported=true, reason=enabled, client=<第三方包名>`（对照：未 hook 时为 `reason=unsupportedClientOrVersion`）。
4. 关闭系统「质感模糊」开关（设置里若可见）：应**不模糊**（证明系统开关判据仍生效）。
5. 「非默认皮肤也模糊」开关：开启后换一个自定义皮肤，键盘背景应模糊；同时检查 AI 卡片 / 翻译 / 分词等界面**无样式错乱**（证明调用栈过滤生效，未污染其他调用点）。
6. 若日志出现 `主锚点未命中，转入白名单反查兜底` → 宿主已改混淆名，确认 `via=fallback:...` 是否命中；两者都失败会打 ERROR 并保持官方行为（不崩、不糊）。
7. 若 `skin` 日志报 `dy0.f 不存在 / dy0.f#f 不存在` → 宿主升级改了混淆名，非默认皮肤开关未生效（需重新锚定）；白名单开关不受影响。

> **勿依据本章回填代码**。slotMetrics 取色告警降噪（属日志问题，非布局）**保留**，见 §11.4。

### 11.1 现象与首轮假设（v1.0.54，已证伪）

开启「面板透明模糊」后，剪贴板工具面板（`px.w` OPPO 面板）布局异常。首轮假设为
「键盘根容器左右内缩、面板被带着变窄居中」，据此实现 `attachFullWidth`（负 margin 撑回
屏宽 + 临时关 `clipChildren`）。**真机日志显示 root 宽度 = 屏宽，假设不成立**
（`attachFullWidth -> 键盘无内缩，面板随根容器通栏挂载（root=1272px/screen=1272px）`）——
横向布局两态完全一致（卡片 x=56..1215、文字左边距 x=116、字号一致），不是宽度问题。

### 11.2 根因：模糊模式下**条目厚度**暴涨（v1.0.55 定位，v1.0.56 验证修复未生效）

用户原话：「**模糊后剪切板里的内容条变宽了，长看着是一样的啊。让宽恢复正常就行了**」——
横向（长）没变，是内容条的**厚度**变了。截图像素取证（1272×2772 / density 3.5，同一面板
同一位置，模糊关 vs 模糊开）：

| 条目卡 | 模糊关 | 模糊开 | 说明 |
|---|---|---|---|
| MusicRW / appshare（单行无芯片） | ≈160px | **≈255px（+55%）** | 文字仍居中、字号不变 |
| URL（两行 + 芯片行） | ≈340px 完整 | 仅剩 ≈124px 且底边齐裁 | 列表溢出视口、末卡被 RecyclerView 裁掉 |

URL 卡可见高度 < 48dp 下限（168px）证明**不是 minHeight 等比放大**，而是列表总高溢出
面板视口（≈732px）后末卡被裁的连锁。

**反编译锚定**（宿主 8.5.303.494）：

- `px/u.java#onBindViewHolder`：`float f4 = he0.p.f39756o / he0.p.f39757p`（selfScale /
  appScale）→ `minimumHeight = 48dp × f4`；字号分支 `tn.h.z(f4)`（LuXun 设备再 ×1.55，
  仅 `fZ < 0.95` 时缩小）；chip 行上边距 `8dp × fZ`、阴影条高 `24dp × fZ`。
- `k71/a.java#C()`（键盘加载/换肤时跑）：`p.f39756o = (p.f39757p × boardPer) / 100`，
  LuXun 竖屏 `boardPer = boardW×100/screenW`。竖屏通栏时 boardW = screenW ⇒ boardPer=100
  ⇒ f4=1（日志实证 `appScale=3.9, selfScacle=3.9`）；**模糊（液态玻璃全高窗口）模式下
  boardPer≠100 ⇒ f4≈1.55**（255px ≈ 48dp×1.55×3.5）。
- 适配器 padding（`16dp × f4`）在**构造时**定格、模糊开关不重建适配器 ⇒ padding 维持正常值
  （实测文字左边距两态一致 116px）。

### 11.3 修复尝试与失败（v1.0.55，已撤销）

后置 hook `px.u#onBindViewHolder`，把被污染的量压回正常值（卡 `minimumHeight` → 48dp、
字号 → 16sp、chip 行上边距 → 8dp、阴影条高 → 24dp），双信号触发（f4 偏离 1 超 3% 且
minHeight 偏离 48dp 超 5%）。**真机验证仍未修好**，用户决定放弃，代码已全部移除。

留待后续若重新立项，可排查的方向（均未验证）：

1. 修 bind 时算的量不够——条目最终高度可能还受面板侧 RV 的 `LayoutParams` /
   `GridLayoutManager` span 尺寸或 `px/w` 视图树在模糊模式下的再测量影响（§11.2 的 URL 卡
   < 48dp 下限即暗示列表级裁切，不只是条目级 minHeight）；
2. `he0.p` 字段读取与 hostScaleRatio 判定链在真机是否真的拿到 f4≈1.55（v1.0.55 未回传到
   有效的 `itemFix` 日志）；
3. 更彻底但侵入性更强的路线：hook `k71/a#C()` 或 `he0.t0` 的 boardPer 计算本身，让模糊
   模式下 boardPer 恒为 100（影响面 = 全键盘所有按 selfScale 缩放的 UI，需谨慎评估）。

### 11.4 保留：slotMetrics 取色告警降噪（v1.0.55，不随本章撤销）

原实现每次键盘弹出刷 2~3 条 W（`系统图标取色不可信 #DCDCDC ... 回退常量色`）。根因：
亮键盘上系统按钮的 drawable **裸渲染**出亮灰 #DCDCDC——着色由 View 的 `imageTintList`
施加、不在 drawable 渲染结果里，过不了明暗校验。改为：渲染色不可信时**改试
`imageTintList`**（才是该主题真实着色）；两者都不可信才回退常量色，且日志降级 D +
每次键盘弹出至多一条（`slotFallbackLogAt`，`setInputView` 时重置）。
