# 天气「隐藏广告 / 隐藏全部运营卡片」移植与实证

> 宿主：`com.coloros.weather2`（天气 17.7.4，`E:/WorkBuddy_All/APP/oneplus/天气_17.7.4.apk`）
> 上游：coloros-mod（MIT）`app/src/main/java/com/rikumi/colorosmod/hooks/WeatherHooks.java#hookWeather`
> 本模块：`hook/hookers/WeatherPurifyHook.kt` + `ui/compose/scopes/apps/WeatherPage.kt`

## 1. 上游做了什么

| 上游开关 | 上游实现 |
|---|---|
| `weather_hide_ads` | after-hook `WeatherWrapper#getOperationsCards()`，过滤 `getCardType() == 6` 的卡片 |

## 2. 本机实证：卡片类型 6 仍是广告

`IndexOperationsItemCreator#create(Context, WeatherWrapper, Object[])`（`file_id=0`,
`method_idx=50319`，343 opcode，未被内联）遍历 `WeatherWrapper#getOperationsCards()`：

```java
// 卡片 5：可关闭的运营卡片
if (card.getCardType() == 5) {
    if (!IndexOperationsManager.getOperationsCardVisibility(card.getOperationsCardMark())) skip;
    ...
}
// 卡片 6：广告
if (card.getCardType() == 6) {
    if (!IndexOperationsManager.getOperationsCardAdVisibility()) skip;   // ← 唯一可见性闸门
    if (!(ctx instanceof WeatherPreviewActivity)) skip;
    if (AppFeatureUtils.isSaleMode()) skip;
    ...
    bannerItem.setAdUid(operationsCardAdList.get(idx));   // 广告位才有 adUid
}
// 卡片 1：分钟级降雨（RAIN_CARD），走 MinutelyRainBannerItem
// 卡片 26 / 4：额外要求 cardBigIcon 非空
```

反汇编原文（关键片段）：

```
invoke-virtual {v19}, OperationsCard;->getCardType()I
const/4 v4, 0x6
if-ne v2, v4, :label_00e8
invoke-static {}, IndexOperationsManager;->getOperationsCardAdVisibility()Z
move-result v2
if-eqz v2, :label_00c8        # false ⇒ 整张卡片跳过
```

`WeatherWrapper#getOperationsCards()` 的返回元素类型确认为
`com.oplus.weather.service.room.entities.OperationsCard`（22 处 `getCardType()I` 调用来自该类，
`BannerItem` 内部调它 26 次），与上游 `(Integer) callMethod(card, "getCardType")` 一致。

## 3. 与上游的差异：为什么要换 hook 点

`WeatherWrapper#getOperationsCards()` 在本机有 **7 个消费方**：

| 消费方 | 用途 |
|---|---|
| `IndexOperationsItemCreator#create` ×2 | 渲染运营卡片 |
| `IndexOperationsManager#supportShowIndexOperations` | **用「list 是否为空」决定整块运营卡片是否显示** |
| `IndexOperationsManager#supportShowWeatherWarnTag` | **用「list 是否为空」决定天气预警标签是否显示** |
| `IndexOperationsManager#exportSupportShowIndexOperations` | 对外导出能力 |
| `ADViewModel#requestDomesticAd` | 广告请求 |
| `NoticeAdImpl$Companion#getNoticeAdImpl` | 公告广告 |
| `InformationImpl$Companion#getInformationImpl` | 资讯 |

`supportShowIndexOperations` 的关键分支（`method_idx=50361`）：

```
getOperationsCards() → isEmpty()
if-eqz v3 → return true     # 非空 = 支持显示
else     → return false     # 空 = 不支持（日志 "operationsCards empty"）
```

⇒ 若沿用上游「过滤 list」，某城市只剩广告卡片时 list 变空，
`supportShowIndexOperations` / `supportShowWeatherWarnTag` 会连带返回 false，
**天气预警标签一起消失** —— 副作用超出「隐藏广告」的范围。

因此本模块改为在渲染判定处拦 `getOperationsCardAdVisibility()` 返回 false：

- 只影响 `cardType == 6` 的广告卡片；
- 数据层 list、预警标签、其它运营卡片全部保持原生；
- `create` 是唯一渲染入口 ⇒ 广告不渲染即不曝光，效果与上游一致。

## 4. 三个 hook 点（最终实现）

| 开关 | 类#方法 | 动作 | 依据 |
|---|---|---|---|
| 隐藏广告 | `indexoperations.IndexOperationsManager#getOperationsCardAdVisibility()Z` | 返回 `false` | 26 opcode，被 `create` 以 `invoke-static` 调用（未内联） |
| 隐藏广告 | `ad.splash.SplashAdManager#enableSplash()Z`（**private**） | 返回 `false` | 184 opcode，`loadAd` 内 `invoke-direct` 调用（未内联） |
| 隐藏运营卡片 | `indexoperations.IndexOperationsItemCreator#create(Context, WeatherWrapper, Object[])` | 返回 `null` | 343 opcode 真实实现；另一个 `create` 是 3 opcode 协变 bridge |

### 开屏广告为什么安全

`SplashAdManager#loadAd(Z, Context, Function0)`（`method_idx=47554`）开头：

```
invoke-direct {v17}, SplashAdManager;->enableSplash()Z
if-nez v1, :label_008e        # true → 正常加载
# false 分支：统计"未请求原因" → reportAdNotRequest("3", reason) → return-void
```

返回 false 时既不请求广告，也不调用 `showSplashPlaceholderIfNeeded`，也不会触达
`activityReference` 等后续逻辑 —— 这是宿主自身关闭开屏时走的路径（非 OPPO/realme 机型、
隐私未同意、非简体中文等条件都在 `enableSplash()` 内部判定），因此不会卡首屏。

### 隐藏运营卡片为什么用 create 置 null

- `IndexOperationsItemCreator#create` 是全 App 构建运营卡片列表的**唯一实现**
  （`method_calls` 里 `IndexOperationsItemCreator#create` 的唯一内部调用者就是它自己的 bridge）；
- 返回 `null` 是宿主认可的「无内容」结果：`create` 结尾在 banner 列表为空时**原生**就
  `return-object v33`（v33 = null）；
- 本机 `create` 内部末尾还会 `appendRealTimeNotifyItem(...)` 追加实时提醒卡片，
  一并隐藏 —— 符合「全部运营卡片」语义。

## 5. 覆盖边界（明确不处理的广告）

| 通道 | 类 | 为什么不处理 |
|---|---|---|
| 信息流 / 横幅广告 | `ad.banner.BannerAdApi#createFeedAdItem(WeatherWrapper)` | 3 opcode 纯转发，返回值被调用方直接 add 进列表，置 null 有 NPE 风险；上游也未处理 |
| 滚动条公告广告 | `ad.NoticeAdImpl#requestAdIfNeed()` + `ScrollBarAdPresenter` | 与公告数据共用同一卡片，拦截会影响公告本身 |
| 原生广告 SDK | `ad.internal.*`、`ad.splash.SplashAdManager#createRequest` | 属 SDK 层，宿主升级易变 |

## 7. 验证要点（真机）

1. 开启「隐藏广告」→ 重启天气：
   - 冷启动不再出现开屏广告（首屏直接是主界面）；
   - 主页运营卡片区内的推广卡片消失，其它运营卡片与天气预警标签仍在。
   - 日志：`WeatherPurify` 三条「已挂 …」；`SplashAdManager` 出现 `load splash stop` 相关 D 日志。
2. 开启「隐藏全部运营卡片」→ 重启天气：主页运营卡片区整块消失（含实时提醒），其余卡片正常。
3. 两个开关都关 → 行为应与原生完全一致（每次调用都 `chain.proceed()`）。
