# 锁屏通知下移 + 桌面隐藏应用四件套

> 移植来源：[rikumi/coloros-mod](https://github.com/rikumi/coloros-mod)（MIT）。
> 宿主实证版本：系统界面 `17.99.02`、系统桌面 `17.3.12`、ColorOS 17 / OnePlus 15。
> 代码：`hook/hookers/KeyguardNotificationOffsetHook.kt`、`hook/hookers/LauncherHiddenAppsHook.kt`、
> `ui/compose/scopes/apps/LockScreenPage.kt`、`ui/compose/scopes/apps/LauncherHiddenAppsPage.kt`。

## 一、锁屏通知区域下移（宿主 `com.android.systemui`）

功能树节点：**「锁屏」**（`lock_screen`，`treeOrder` 内，标题 `R.string.LockScreen`）。
开关 + `0..40dp` 滑条（默认 20dp），开关与滑条都在 `SettingsPrefs`。

### 三条通道缺一不可

| 状态 | 方法 | 说明 |
|---|---|---|
| 静止 / 拖拽 / 收起 | `shade.NotificationPanelViewController#getKeyguardNotificationStaticPadding()I` | 只有 `isKeyguardShowing()==true` 才叠加 |
| 锁屏通知中心（展开） | `OplusLockscreenShadeTransitionControllerExImpl#getNtfTopPaddingInLockscreen()I` | 新实现 |
| 锁屏通知中心（收起动画） | `…#getNtfTopPaddingInLockscreenNtfCenter()I` | 新实现 |

旧实现 `statusbar.OplusLockscreenShadeTransitionControllerEx` 两个方法也在，作为 OTA 回退兜底。

### 两个必须注意的点

1. **`getKeyguardNotificationStaticPadding` 必须判 `isKeyguardShowing`**：非锁屏时它原始返回值
   就是 0，无脑叠加会污染下拉通知栏（上游注释明确踩过）。
2. **`isKeyguardShowing` 必须 `callDeep`**：该方法声明在面板基类，VC 的 `declaredMethods` 里没有；
   用 `callByName` 恒 null ⇒ 表现为「非锁屏也偏移」。

单位：设置存 dp，hook 侧 `Math.round(dp * density)`。三条都做 300ms TTL 缓存
（`offsetPx()` 是布局期高频出口，拖拽通知栏时每帧都会问一次）。

## 二、桌面隐藏应用四件套（宿主 `com.android.launcher`）

功能树：挂在 **「系统桌面」→「隐藏应用」** 二级入口（`launcher_hidden_apps`，**不进 `treeOrder`**，
否则会出现两个同名顶层节点）。

| 功能 | 钩子 | 本机适配 |
|---|---|---|
| 桌面双指张开打开隐藏应用 | `DragLayer#dispatchTouchEvent(MotionEvent)Z` | `ScaleGestureDetector`，`accum>1.2f && spread>100dp`；仅 NORMAL 态 |
| 多任务显示已隐藏应用 | `qp.c#i(Task)Z` | **类在 DEX 根包**，不是 `com.android.quickstep.qp.c` |
| 彻底隐藏所选应用图标 | `LauncherApps#getActivityList` + `OplusAppFilter#shouldShowApp` | 双通道，缺一漏图标 |
| 彻底隐藏应用列表 | —— | 纯 UI 页（应用多选），hook 只提供名单读取 |

### ⚠️ 五个已修正的致命坑（v1.2.8 修复，勿回退）

1. **`qp.c` 在 DEX 根包**：描述符 `Lqp/c;`，Java 全限定名就是 `qp.c`。
   写成 `com.android.quickstep.qp.c` 在本机 `classes` 表 0 行 ⇒ `classOrNull` 恒 null
   ⇒ hook 静默不装、零日志。单例经 `qp.c$c->a` 暴露。
2. **`qp.c#i` 的语义已反汇编确认**：入参 `Task`，内部用
   `Task.getTopComponent()` + `TaskKey.e()`/`q`（userId）查三份隐藏名单，命中返回 true。
   被 `OplusRecentsViewImpl#shouldSetAlphaTo1` 与 `OplusTaskThumbnailViewImpl#checkAndUpdatePrivacy`
   调用 ⇒ 这就是多任务渲染路径。
   **只挂 `i(Task)`，不要挂 `g(int,String)`** —— 后者是手势保护路径（点隐藏应用不截屏/不进最近任务），
   放开会让隐藏应用被截屏。
3. **`OplusAppFilter#shouldShowApp` 有 4 个重载**，`declaredMethods` 里 `(String, UserHandle)Z`
   排在 `(ComponentName, UserHandle)Z` 之前。用 `findMethod(name, 2)` 会拿到 String 版、
   随后签名校验判不符 ⇒ 直接跳过 ⇒ 功能静默失效。**必须用 `findMethodByShape` 精确取**，
   且 `UserHandle` 用编译期引用（传 null 会退化成「该位置任意」，丢掉关键约束）。
4. **`isModelLoaded()` / `forceReload()` 声明在父类 `LauncherModel`**：`getModel()` 返回子类
   `OplusLauncherModel`。用 `callByName` 恒 null ⇒ 永远判「模型未就绪」⇒ 20 次重试后超时放弃
   ⇒ 现象「改完名单回桌面图标还在」+ 只有一行超时 W 日志。**必须 `callDeep`**。
5. **`getActivityList` 不要原地 `removeAll`**：宿主可能返回
   `Collections.unmodifiableList` / `Arrays.asList`，原地改抛 `UnsupportedOperationException`
   （被 `runCatching` 吞掉 = 静默不过滤）。改为**返回新 `ArrayList`**。

另：双指张开**必须读开关**（曾漏掉，导致开关形同虚设、手势无条件生效）。

### 双指张开入口（`DeepProtectedAppsManager`）被混淆

- 单例：`k(Context)` **static**（`access_flags=0x19`），返回自身类型；上游 `getInstance(Context)` 本机不存在。
- 打开：`N(Launcher)V` 实例方法（`access_flags=0x11`）；上游 `showHideApps(Context,boolean)` 本机不存在。
- 两者都按「先原名、再混淆名」探测，并校验 `isStatic` / 参数类型 / 返回类型。

### `isInState` 必须 callDeep

声明在 `com.android.launcher3.statemanager.StatefulActivity`（`Launcher` → … → StatefulActivity）。
`LauncherState.NORMAL` 是静态字段，取法 `Reflect.findField(stateCls,"NORMAL")?.get(null)` + 缓存。

### 模型刷新策略（与上游不同）

上游用跨进程快照 + 100 次重试等待链。本实现改为 hook **`Launcher#onResume`** 后对比
「上次已应用名单」→ 变了才刷；模型未就绪时 300ms × 20 次重试。
理由：名单只能在模块 App 里改，「切回桌面」是必然发生的时机，简单且不与启动期装载撞车。
**冷启动第一次 resume 只记基线不刷新**（本次装载已过滤过，刷新纯属浪费）。

名单查询加 **1s TTL 缓存**（`shouldShowApp` 对每个图标调用一次，一次装载几百次）；
`onResume` 时同时失效名单缓存与触摸门控缓存（300ms）。

### 名单存储

`SettingsPrefs["hidden_launcher_components"]` = **StringSet**，元素 `ComponentName.flattenToString()`
即 `包名/类名`。总开关 `hidden_launcher_apps_enabled` **关闭时必须返回空集**（不能只靠 UI 置灰，
否则用户关掉开关后图标仍不出现、无从恢复）。

UI 写名单时若非空则**强制把总开关置 true**（对齐上游 `HiddenAppsScreen.save()`）——
只写名单不开开关属于典型「操作无反馈」。选择器回传包名级，保存时保留既有精确组件、
新增包补 `getLaunchIntentForPackage` 的默认入口。

## 三、验证记录

| 版本 | 结论 |
|---|---|
| v1.2.6(134) | 首次落地，编译通过 |
| v1.2.8(136) | 修正上述 5 个致命坑 + 2 处性能缓存 + 1 处开关门控；`assembleDebug` 通过；产物内确认 `qp.c` 字符串、`pinchOutEnabled`/`computeOffsetPx`/`densityPx` 方法均已编入 |

真机验证清单（待用户实测）：
- 锁屏：开关打开后静止态通知下移；下拉拖拽；锁屏通知中心展开/收起；关掉开关立刻复原。
- 桌面：双指外张进隐藏应用文件夹（关闭开关则无反应）；多任务里能看到隐藏应用卡片且不透明；
  彻底隐藏后桌面/抽屉/搜索均消失，切回桌面图标立即消失；清空名单后恢复。
