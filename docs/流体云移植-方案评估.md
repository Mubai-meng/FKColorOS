# 流体云两功能移植 · 方案评估

> 移植来源：`E:/WorkBuddy_All/workbuddytask/FuckColoros/fkfluidcloud`（原 FKColorOS / FuckColorOS 模块）
> 目标模块：ColorOSTools（`com.fr.colorostools`，libxposed API 102 现代模块）
> 逆向素材：`E:/WorkBuddy_All/APP/oneplus`（ColorOS 17 / OnePlus 15，智慧决策服务 = `com.oplus.metis` 已完整反编译）
> 结论先行：**hook 方案即为当前最优雅可行方案**；按 ColorOS 17 实测把参考实现的「3 宿主 × 多点」收敛为「**metis 单宿主**」，并做 3 项性能/稳定性优化（详见 §4）。

---

## 1. 两个功能是什么

| 功能 | 用户视角 | 系统内真实链路（metis 进程，text_intent） |
|---|---|---|
| **替换流体云目标** | 复制 B 站链接出的流体云卡片，「打开」跳到平替 App（如 PiliPalaX）而不是原 App | 复制文本 → `TokenDetector.process()` 规则匹配 → `Repository#obtainKouLingData` 在线取卡片 VO → `CommandHandler#checkValidity`（决定「打开卡」还是「安装卡」）→ `DeepLinkData#parseIntent` 构建跳转 `TextIntent` → `Seedling.Builder.build` 出卡 |
| **自定义流体云** | 给剪切板场景加自定义规则（正则 + 目标 App），让系统本不出卡的内容（如 v2ex 链接）也出卡片 | 同上链路；自定义规则在服务器没有卡数据，必须**自己造 VO** 并让系统「认得出」这条内容 |

## 2. 候选路线对比（有没有更优雅/更小影响的方案？）

| 路线 | 做法 | 评估 |
|---|---|---|
| **A. 改系统配置文件（零 hook）** | `TokenDetector#readTokens()` 的规则来自本地缓存文件 + 内置 JSON（已反编译核实），直接改文件注入规则 | ❌ 不可行：① 写 `/data/data/com.oplus.metis/` 需要 root，LSPosed 模块不应假设 root；② 会被云端 `updateNewRules(String)` 覆盖；③ 改文件后需重启宿主进程才生效，且「造卡片」仍然缺在线数据，还是得 hook 取数环节 |
| **B. 走系统自带设置项** | 流体云设置页若有「自定义规则」入口则直接配置 | ❌ 不存在：ColorOS 17 设置页（metis）没有自定义规则 UI——这正是原版模块存在的理由 |
| **C. 只 hook 一处** | 每个功能只保留一个注入点 | ❌ 不可省：功能二「识别（TokenDetector 注入 RuleVO）→ 取数（Repository 喂 VO）」是串联依赖，缺一不可；功能一「卡片定性（checkValidity 改 VO）→ 跳转目标（parseIntent 改 TextIntent）」同样串联 |
| **D. 移植参考实现（hook）** | 按 17 实测收敛后的单宿主 hook | ✅ **采纳**。事件驱动（仅在「复制文本/切前台」时触发，分钟级频率），不碰 per-frame / per-binder 热路径；关闭状态仅多一次 volatile 布尔判断 |

**结论：hook 是唯一可行且已足够优雅的方案。** 真正影响「优雅度/性能」的不是 hook 本身，而是参考实现里的三处浪费——按 ColorOS 17 实测全部收敛（见 §4）。

## 3. ColorOS 17 实测核实（全部基于反编译素材，非推断）

### 3.1 引擎类分布 → 作用域只需 `com.oplus.metis` 一个

对 17 的两个候选宿主 APK 做 dex 探针（grep 类描述符）：

| 类 | 智慧决策服务 metis | 智慧数据增强服务 sceneservice |
|---|---|---|
| `textintent.detect.datasource.Repository` | ✓ | ✗ |
| `textintent.distribution.bean.DeepLinkData` | ✓ | ✗ |
| `textintent.distribution.bean.ActionData` | ✓ | ✗ |
| `textintent.manager.helper.CommandHandler` | ✓ | ✗ |
| `textintent...ServiceKouLingLinkVo` | ✓ | ✗ |
| `ointent.token.TokenDetector` | ✓ | ✓（仅识别层） |
| `coloros.direct.command.*`（新引擎） | ✗ | — |

两个功能的核心链路（Repository / DeepLinkData / ActionData / CommandHandler / VO）**只存在于 metis**。
参考实现给 3 个宿主（metis / sceneservice / colordirectservice）都装钩子，在 17 上其中 2 个纯属浪费（类不存在还要打日志）。
→ **本移植只声明 `com.oplus.metis` 一个作用域**：注入进程数 3 → 1，注入面积和日志噪音同步下降。

### 3.2 注入点签名逐条对上（ColorOS 17 实测值）

| 注入点 | 17 实测签名 | 与参考实现 |
|---|---|---|
| `Repository#obtainKouLingData` | `(Context, TextContent, a) -> Object`（挂起函数） | 一致（按形状定位，不靠方法名） |
| `TokenDetector#readTokens` | `private void readTokens()`，字段 `ArrayList<RuleVO> ruleList` | 一致 |
| `CommandHandler#checkValidity` | `private boolean (ServiceKouLingLinkVo, TextContent)` | 一致（private 不影响 hook） |
| `DeepLinkData#parseIntent` | `public TextIntent parseIntent(Context)` | 一致 |
| `ActionData#parse` | 返回 `List<TextIntent>` | 一致 |
| `PlatformBeen` 构造器 | `(String, int, String, String, int, CardIcon, String, List)` | 一致 |
| `CardIcon` 构造器 | `(String, String)` | 一致 |
| `RuleVO` 构造器 | `(int, List<Expression>, String, Integer)` | 一致 |
| `Expression` 构造器 | `(long, String, List<String>, Integer)` | 一致 |
| `ServiceKouLingLinkVo` | **仅 1 个 24 参构造器，无无参构造** | → 必须 Unsafe 分配（见 §4.3） |
| `TextIntent` setter | setPackageName/setAppName/setInstalled/setIntent/setDeepLink/setAppIcon/setPlatformType/setSupport/setSystem 全在 | 一致 |

### 3.3 附带发现（影响功能二写法）

- `readTokens()` 原版有 `if (ruleList != null) return` **早退**：每进程只真正加载一次规则。
  但参考实现的钩子体挂在 `readTokens` **返回后**，于是**每次检测事件都重复执行一遍注入逻辑**（重建 existing 集 + 反射扫描，约 2N 次反射/次）。→ §4.2 修。
- `checkValidity` 末尾 `return !contains(appPackage, topApp)`：**复制时目标 App 正在前台 → 卡片判无效**（不跳自身）。这是系统语义，自定义规则的 appPackages  accordingly 填写即可，无需处理。
- 输入文本长度上限：含 http 的 5000 字符，否则 400。自定义正则可放心匹配长文本。

## 4. 相对参考实现的收敛与优化（更优雅 / 更小影响）

### 4.1 单宿主（3 → 1）
只注入 `com.oplus.metis`。`scope.list` 只加一个包名；`MainHook.onPackageReady` 只在这一包名下安装。
（新引擎 `direct.command` 类在安装时仍会探测一次——类查找失败会被 Reflect 缓存，零成本；将来系统换代自动接上。）

### 4.2 `readTokens` 钩子改「指纹 + 实例身份」双判，未变化零反射
钩子体缓存 `(ruleList 实例 identity, 生效规则指纹)`；两者都没变直接 return。
- 系统云端更新规则（`updateNewRules` 替换 ruleList 实例）→ 身份变化 → 自动重新注入，不丢规则；
- 常规检测事件 → 直接返回，**反射调用从 O(N)/次 降为 0**。

### 4.3 VO 构造去 HostGson 依赖
`ServiceKouLingLinkVo` 无无参构造 → 参考实现靠宿主 Gson `fromJson("{}")`（metis 的 Gson 常被 R8 删掉，实际多走 Unsafe 兜底）。
本移植**直接用 Unsafe `allocateInstance` + setter/字段填充**（`ref/Reflect.kt` 已具备），少一个宿主动态依赖；`PlatformBeen` 改写在两处钩子里都走「就地写字段」（参考实现原文：效果等价），不做 JSON 往返。

### 4.4 诊断钩子默认不挂
参考实现有 4 个 verbose 诊断点（checkValidity 探针 / LogUtil 转发 / Seedling.Builder 探针 / detectInner）。本移植 v1 **不挂**——行为钩子本身已对每种失败原因写日志（类不存在 / 形状对不上 / 未命中规则 / 字段体检未通过），排障信息已够；挂诊断点属于「排查时才需要」的额外面积，留给后续详细日志开关。

### 4.5 开关语义对齐本模块既有约定
- 两个功能各一个总开关（默认**关**，对齐「其他设置默认关闭」的既有决定）；
- 钩子**常驻安装**（不随开关卸载），钩子体第一行 volatile 布尔早退——改开关**无需重启 metis**，与参考实现「改规则也不用重启」一致；
- 规则 JSON 存 `SettingsPrefs`（remote prefs），hook 侧 `HookEnv.settingString` 直读，与既有开关同源，无额外同步通道。

## 5. 性能影响结论

| 维度 | 影响 |
|---|---|
| 安装期（metis 启动一次） | 5 个方法钩子（obtainKouLingData / readTokens / checkValidity / parseIntent / parse），微秒~毫秒级 |
| 运行期（每次「复制文本/切前台」检测） | 功能关：各钩子 1 次 volatile 读后 return。功能开：1 次规则查表（3s TTL 缓存）+ 几次反射取字段 + 正则匹配——相对系统自身同事件发起的**网络请求**可忽略 |
| 热路径 | 不碰。无 per-frame（磁贴/动画）、无 per-binder（AMS/WMS 调用）钩子 |
| 内存 | 规则 JSON 数 KB；指纹缓存一个字符串 |
| 稳定性 | 任何一步失败都 `chain.proceed()` 放行原逻辑（不产残缺对象、不让挂起函数返回 null），最坏情况退化为「功能不生效」而非崩溃 |
