# 熄屏挂机（假熄屏）移植 — 方案与实证

> 目标：按电源键**只熄灭屏幕**，系统与 App 继续运行（不被冻结 / 不降频），用于游戏挂机、下载、跑任务。
>
> 上游参照：`https://github.com/chuyb-re/fakeScreen`（下文称「上游」）。
> 适配宿主：ColorOS 17 / OnePlus 15 / Android 17（SDK 37）。
> 适配素材：`E:\WorkBuddy_All\APP\oneplus\{services.jar, oplus-services.jar, framework.jar}`。
> 落地版本：**FKColorOS v1.1.15(85)**。

---

## 零、设计总则：只碰内存，绝不落盘

本功能唯一的硬约束是用户的原话：**「不要对我手机造成不可逆的影响」**。

由此推导出「四个不写」：

| 不写什么 | 为什么 |
|---|---|
| 不写 `Settings.System.SCREEN_OFF_TIMEOUT` | 那是**用户的设置项**。进程中途死亡就永久污染（屏幕永不熄屏），得用户自己进设置改回来 |
| 不用 `Settings.Global` 存任何**运行状态** | 只存「待命开关」这一个用户显式选择，值域 0/1，用户可见可清 |
| 不改系统 / 应用 APK | 全部运行时 hook |
| 不留后台服务 / 定时任务 / 闹钟 | 只在 system_server 内挂 5 个内存钩子 |

**唯一的持久化写入**是 `Settings.Global["colorostools_fake_screen"]`（0/1），
存的是用户的**开关选择**，不是运行状态。它是可读可清的普通设置项，用户随时
在设置里能清掉，不构成任何不可逆影响。

## 一、两个状态位（本版核心，别混用）

| 状态 | 含义 | 持久化 | 谁改 |
|---|---|---|---|
| `armed` | **待命开关** = 磁贴是否打开 | **是**（`Settings.Global[colorostools_fake_screen]`） | 只由磁贴广播改 |
| `fakeOffActive` | **当前是否正处假熄屏** | 否（纯内存） | 只由电源键 / 系统接管改 |

```
磁贴打开 ⇒ armed=true          ⇒ 屏幕毫无反应，只是「下次按电源键会假熄屏」
按电源键 ⇒ fakeOffActive 翻转   ⇒ 屏幕灭 / 亮
磁贴关闭 ⇒ armed=false         ⇒ 屏幕毫无反应，电源键立刻回归系统原生
```

拆开这两个位的意义（用户明确要求）：
**磁贴是功能开关，不是「立即熄屏」按钮**。在控制中心误触就黑屏是不可接受的；
熄屏只能由电源键触发，行为才可预期。

进程重启时两类状态**区别对待**：`fakeOffActive` 无条件复位（物理屏必然已亮），
`armed` 从 `Settings.Global` **读回**（那是用户的开关选择，不能被重启抹掉）。

## 二、结论先说

| 项 | 结论 |
|---|---|
| 上游能否直接用 | **不能**。`powerPress` 签名不匹配 ⇒ 方法恒 null ⇒ 静默失效；`getInternalDisplayToken` 已被移除 |
| 唯一汇聚点 | `com.android.server.policy.PhoneWindowManager#powerPress(J I I)` |
| 熄屏手段 | `SurfaceControl.setDisplayPowerMode(token, 0)` —— 直改显示电源模式，**不进 Doze、不释放 wakelock、不冻结进程** |
| **触发方式** | **只由电源键触发**。磁贴是开关，不直接改屏 |
| **恢复方式** | **再按一次电源键**（翻转语义），零学习成本，不引入任何新交互 |
| 翻转判据 | 「`PowerManager#isInteractive()` + 自身标记」组合，**不依赖**任何物理屏读数 |
| 多击判别 | hook `PowerKeyRule#onMultiPress` 置一次性标记；**不能**数 `powerPress` 调用次数 |
| 屏幕超时 | hook `PowerManagerService#getScreenOffTimeoutLocked` 返回值，**纯内存、零持久化** |
| 来电 / 闹钟 | **不自动点亮**（用户明确要求：挂机时屏幕不该突然亮起） |
| 宿主 | **`system`（system_server）**，写 `android` 会完全不生效 |
| 开关 | **磁贴**（用户级功能开关）+ remote prefs 键 `fake_screen_enabled`（模块级总闸） |
| 入口 | 「其他」页 → 模块内置磁贴列表 → 熄屏挂机（`TileService`） |
| 钩子总数 | **5 个**（更早版本 6 个，其中 3 个自愈钩子已合并为 1 个同步点） |

## 三、单击链路（两条互斥路径）

```
非早发：SingleKeyGestureDetector → PowerKeyRule#onKeyGesture → onPress
         → IInputExt#powerPress → PhoneWindowManagerExtImpl#oplusPowerPress
         → sendGoToSleepDelayMessage（延时）→ IPhoneWindowManagerWrapper#powerPress
         → 【PWM#powerPress(J I I)】

早发：  PowerKeyRule#onKeyUp →（mShouldEarlyShortPressOnPower 且 count==1）
         → 【PWM#powerPress(J I I)】；同时 onPress 第一行直接 return
```

`PowerKeyRule#onPress` 反编译实证：

```
:label_0009
    iget-object v0, ... mShouldEarlyShortPressOnPower
    if-eqz v0, :label_0009        # 早发模式下 onPress 直接 return
    return-void
...
    const/4 v5, 0x1               # ← count 硬编码为 1
```

## 四、多击判别（本实现最关键的一处修正，踩过两个错）

### 4.1 错误方案 1：读 `powerPress` 的 `count` 参数

`PWM#powerPress(J I I)` 第 3 参形参名为 `count`，直觉上双击应传 2。但实证：

```smali
# PowerKeyRule#onPress
const/4 v5, 0x1                                   # 单击路径硬编码 1
invoke-interface IInputExt->powerPress(JZII)V

# PowerKeyRule#onMultiPress
move-wide v2, v8
move v5, v10                                      # ← 多击路径传真实值
move v6, v11

# PhoneWindowManagerExtImpl$OplusPowerKeyHandler#handleMessage
const/4 v7, 0x1                                   # ← Oplus 又压回 1
invoke-interface/range {v3 .. v8}, IPhoneWindowManagerWrapper->powerPress(JZII)V
```

⇒ 单击走 Oplus 时 count 恒为 1；多击虽然 `onMultiPress` 传了真实值，但
`OplusPowerKeyHandler` 同样压成 1，且两条路径最终都只调 `powerPress` **一次**。
**从 `powerPress` 的参数根本读不出真实点击次数。**

### 4.2 错误方案 2：数 `powerPress` 被调几次

`SingleKeyGestureDetector` 非早发模式下会把 `pressCount` 攒到 2，只调用**一次**
`completeDelayedPress` ⇒ `onMultiPress` ⇒ 最终也只到 `powerPress` **一次**。
⇒ 双击会被误判成单击并熄屏。

### 4.3 最终方案：`onMultiPress` 一次性标记

```
onMultiPress 被调用 → multiFlagAt = now（然后 proceed，多击手势保持原生）
powerPress  被调用 → 标记存在 ⇒ 消费并 proceed（多击那一次，不熄屏）
                    标记不存在 ⇒ 单击，切假熄屏，返回 null 阻止原生休眠
```

- **一次性**（消费后立即清零）而非时间窗：多击手势只对应一次 `powerPress`，
  消费掉就不会波及紧随其后的正常单击。
- **`MULTI_FLAG_TTL_MS = 2000ms` 兜底过期**：防某版本改了调用关系后标记永久残留，
  那会让单击彻底失效（最大风险点）。

## 五、熄屏手段与恢复模型（本版重点）

### 5.1 为什么用 `setDisplayPowerMode` 而不是 `goToSleep`

`goToSleep` 会释放 wakelock、进 Doze、冻结后台 App —— **挂机就失效了**。
`SurfaceControl.setDisplayPowerMode(token, POWER_MODE_OFF)` 只改物理屏电源模式，
CPU 与进程完全照常，这才是「假熄屏」的语义。

代价：**在切屏这一刻，系统不知道屏幕灭了**。

### 5.2 恢复方式：电源键翻转 + 单一状态同步点

**恢复动作就是「再按一次电源键」**，不引入任何新手势 / 通知 / 悬浮球 / 超时自动恢复。
理由：电源键本来就是「熄屏 ⇄ 亮屏」的翻转键，用户已有肌肉记忆，零学习成本；
而任何额外入口都是新增失效面。

#### 电源键的四层早退（顺序即优先级）

| # | 条件 | 动作 | 理由 |
|---|---|---|---|
| 1 | **未待命**（磁贴关闭） | `proceed()` | 用户要求「关磁贴后恢复正常电源键」 |
| 2 | 本次是多击 | `proceed()` | 多击手势原样交还系统 |
| 3 | 系统真的睡了（`!isInteractive`） | `proceed()` | **只有系统能正确唤醒**（要退 Doze、恢复 wakelock），我们直调只会得到「屏亮着但 CPU 仍睡」 |
| 4 | 其余（清醒 + 待命） | **翻转**，返回 null | 阻止原生锁屏 / 休眠 |

第 3 条同时是自愈点：若真出现「系统睡了但标记还残留 true」，交给系统正常唤醒，
随后 `hookDisplayPowerState` 会看到 `setScreenState(非 OFF)` 自动清掉标记，
下一次按键恢复正常的灭屏语义。

#### 判据为什么不能只读一个 API

本机 `framework.jar` 实证 **`SurfaceControl#getDisplayPowerMode` 并不存在**
（只有 setter 与 `nativeSetDisplayPowerMode`），拿不到「物理屏当前电源模式」这个最直接的读数。
其余候选各有偏差：

| 读数 | 假熄屏时会怎样 | 能否直接用 |
|---|---|---|
| `PWM#isScreenOn()` → `DisplayPolicy#isScreenOnEarly()` | 仍返回 **true**（是系统视角） | ✗ 永远判成「亮着」⇒ 只灭不亮 |
| `PowerManager#isInteractive()` | 仍为 true（我们绕过了 PMS 睡眠流程） | ✗ 同上 |
| 自身 `fakeOffActive` 标记 | 正确 | ✓ 但需防漂移 |

所以只读一个 API 都不够，必须用「系统清醒 + 自身标记」组合。

#### 标记漂移由 1 个同步点兜住

「我们改屏」与「系统改屏」走两个**互不相交**的通道：

| 谁在改屏 | 走哪条路 | 会经过 `DisplayPowerState#setScreenState` 吗 |
|---|---|---|
| 本功能（假熄屏 / 点亮） | 直调 `SurfaceControl#setDisplayPowerMode` | **不会** |
| 系统（真休眠 / 真唤醒 / 其它组件强制亮屏） | `DisplayPowerState#setScreenState` | **一定经过** |

⇒ 只需 hook `DisplayPowerState#setScreenState`：一旦它要把屏幕设成**非 OFF**，
说明系统正在接管屏幕，我们就清标记、**不跟系统抢屏**（抢屏会闪一下甚至黑屏）。

**这一个钩子替代了上一版的三个**（`finishedGoingToSleep` / `screenTurnedOff` / `screenTurnedOn`），
因为它们三个都只是 `setScreenState` 的下游副作用。

#### `setScreenState(II)` 参数顺序实证

`hookDisplayPowerState` 读 `chain.args[0]` 当 state，此顺序已双重核对：

```smali
# DisplayPowerState#setScreenState(II)V   .registers 6  ⇒ p0=v3(this), p1=v4, p2=v5
iput v4, v3, Lcom/android/server/display/DisplayPowerState;->mScreenState:I
                                                    # ↑ v4 = 第 1 个参数 = state

# 调用方 DisplayPowerController#setScreenState（DPC 内）
invoke-virtual {v0, v14, v15}, DisplayPowerState;->setScreenState(II)V
                                                    # v14 = state（同函数内已用于
                                                    #   debug.tracing.screen_state /
                                                    #   setReportedScreenState / noteScreenState）
                                                    # v15 = brightness
```

### 5.3 来电 / 闹钟：按用户要求**不**自动点亮

上一版 hook 了 `startedWakingUp` / `goToSleep` 强行退出假熄屏让屏幕亮起，本版**移除**：

- 用户明确要求「来电 / 闹钟时屏幕不需要自动点亮」—— 挂机时屏幕突然亮起会中断挂机；
- 这两个钩子在「正常锁屏」时也会触发，属于**误伤面**，去掉更安全、钩子更少；
- 要看屏幕时按电源键即可（翻转语义），行为可预期。

唯一副作用：来电时屏幕黑着、铃声照常响，按一次电源键即可看到来电界面。

### 5.4 不会自我误触发（已验证）

`screenTurnedOff` 的**唯一**外部调用者是 `DisplayPowerController#setScreenState`：

```
DisplayPowerController#setScreenState → WindowPolicy#screenTurnedOff
Notifier#lambda$handleLateInteractiveChange$7 → WindowPolicy#finishedGoingToSleep
```

而假熄屏走 `SurfaceControl#setDisplayPowerMode` 直调 native，**绕开了 DPC 状态机**，
所以 `hookDisplayPowerState` 不会被我们自己的动作触发（否则一进假熄屏就自我取消）。

## 六、屏幕超时：改为 hook 返回值，不写用户设置

### 6.1 为什么必须处理

假熄屏绕过 DPC，系统仍认为屏幕亮着 ⇒ `SCREEN_OFF_TIMEOUT` 照常倒数
⇒ 到点**真睡眠** ⇒ App 被冻结 ⇒ 挂机失效。所以必须延长超时。

### 6.2 上一版做法的问题（不可逆风险，故弃用）

上一版直接写 `Settings.System.SCREEN_OFF_TIMEOUT = Int.MAX_VALUE`，
再靠内存 + `Settings.Global` 双备份还原。三个问题：

1. 改了**用户的设置项**，在「设置 → 显示 → 息屏时间」里会看到异常值；
2. 若进程在假熄屏期间被杀且备份写失败 ⇒ `MAX_VALUE` 永久留在系统
   ⇒ **屏幕从此不自动熄屏**，得用户自己进设置改回来（正是用户最担心的情况）；
3. `getScreenDimDurationLocked` 内是 `long-to-float` 再 `float-to-long`
   （`Math.min(maxDimDuration, timeout * maxDimRatio)`），`MAX_VALUE` 量级转 float
   会丢精度，dim 时长可能算出异常值。

### 6.3 本版做法

hook `PowerManagerService#getScreenOffTimeoutLocked(J J)J`，假熄屏期间把返回值
顶成 `FAKE_OFF_TIMEOUT_MS`：

- 该方法全类**仅 1 个重载**，主调用方就是 `updateUserActivitySummaryLocked`
  （超时计时器的**唯一**重算点），命中率 100%；
- **纯内存返回值**，不碰任何持久化存储 ⇒ 进程重启自动复原，**无需任何还原逻辑**；
  也就不存在「备份丢了污染系统」这条路径；
- **生效条件 = `fakeOffActive` 为真**，即「只在屏幕已被我们假灭时保护」。
  不按 `armed` 保护是刻意的：待命但屏幕亮着时，系统按用户设定正常熄屏是**正确行为**；
  若也保护，就会出现「打开磁贴后忘了，屏幕亮 12 小时」的耗电事故；
- 只在「系统算出的值比我们的更短」时才顶长，绝不缩短用户原本设的长超时；
- 取 **12 小时**（而非 `MAX_VALUE`）：既远超任何挂机时长，又落在 float 尾数精度
  舒适区内，不踩 §6.2 第 3 条的精度坑。

进入 / 退出假熄屏时各触发一次 `PowerManager#userActivity` 让计时器**立即重算**，
否则新返回值要等下一次自然重算才生效。`userActivity` 在「系统认为屏幕亮着」的
前提下只重置计时器、不会点亮屏幕，安全。

> 已排除的两条看似可行路径：
> - `ScreenTimeoutOverridePolicy` —— 配置值来自编译期资源 `0x10e014e`，运行时改不了；
> - `setUserActivityTimeoutOverrideFromWindowManager(J)` —— 语义是 `Math.min`，
>   只能缩短不能延长，方向相反。

## 七、跨进程通信（磁贴 ↔ system_server）

| 方向 | 载体 | 常量 |
|---|---|---|
| 磁贴 → system_server | 定向广播 `setPackage("android")` | `ACTION_SET_ARMED` / `EXTRA_ARMED` |
| system_server → 磁贴 | `Settings.Global["colorostools_fake_screen"]`（1/0） | `GLOBAL_KEY` |

广播带的是**目标状态**而非「翻转」指令：磁贴点击时用户看到的是已知状态，
发目标状态可避免首次点击时两端对当前值理解不一致导致「点了没反应」。

接收器用 `Context.RECEIVER_EXPORTED`（发送方是模块 App，不同 uid）。外部应用理论上
可伪造这条广播，但效果至多等价于「用户点了控制中心磁贴」—— 切换待命态，
**已不再有「直接熄屏」这条可利用路径**。

### 取消待命时的一个必要收尾

取消待命时若正处假熄屏，**必须先点亮屏幕再交还电源键**：

```
磁贴关闭 ⇒ armed=false
        ⇒ 若 fakeOffActive=true：applyDisplayPower(false) 先亮屏
        ⇒ 之后 powerPress 全部 proceed() 归系统
```

不做这一步会留下「屏幕黑着、电源键已归系统」的死锁：系统视角屏幕仍算「亮」，
按电源键走原生 `goToSleep`，DPC 判定 `targetState == currentState` 可能直接返回，
屏幕就不亮了。

关磁贴时屏幕亮一下是**预期行为**（等于「干净退出这个功能」），且只在
「正在挂机时关磁贴」这一种情况下发生 —— 平时开关磁贴屏幕毫无反应。

## 八、作用域（最容易踩的坑）

`app/src/main/resources/META-INF/xposed/scope.list` 必须包含 **`system`**：

- `system` → 系统框架 = **system_server**（`onSystemServerStarting` 在这里触发）
- `android` → ChooserActivity / ResolverActivity 等系统弹窗进程，**不是** system_server

写错成 `android` 的后果：`onSystemServerStarting()` 永不触发 ⇒ `FakeScreenHook.install()`
永不执行 ⇒ 功能完全不生效，且**日志里连一行报错都没有**。

## 九、装载点一览（共 5 个钩子）

| # | 钩子 | 时机 | 作用 | 缺失后果 |
|---|---|---|---|---|
| 1 | `PWM#init(Context, WindowManagerFuncs)` / `init(Injector)` | proceed 后，全挂 | 取 `mContext`、读回待命态、注册磁贴广播 | 磁贴不可用、待命态不恢复（退化但不致命） |
| 2 | `PWM#powerPress(J,…)` 按形状匹配 | 拦截 | **执行点**：待命时翻转假熄屏 / 否则放行 | **功能完全失效** |
| 3 | `PowerKeyRule#onMultiPress` | proceed 前 | **判别点**：待命时置一次性多击标记 | 双击会误熄屏 |
| 4 | `DisplayPowerState#setScreenState` | proceed 后 | **唯一状态同步点**：系统接管屏幕 ⇒ 清标记 | 标记漂移（退化但有 `isInteractive` 兜底） |
| 5 | `PMS#getScreenOffTimeoutLocked` | proceed 后 | 假熄屏期间延长超时 | 超时到点会真睡眠，挂机中断 |

`powerPress` + `onMultiPress` 是**关键钩子**（缺一即告警 `E` 级日志）；
另三个是**健壮性钩子**（缺失只降级，功能仍可用）。

所有钩子各自独立 `runCatching`：取不到 token / 反射失败只记日志并**原样放行**
（退化为原生电源键），绝不让 system_server 崩或卡。

## 十一、已知限制

1. `POWER_MODE_NORMAL` 取 AOSP 稳定值 `2`（`SurfaceControl` 的电源模式常量未在
   `framework.jar` 中暴露为 Java 字段，无法反编译核对）。若真机点亮后屏幕异常，
   优先怀疑此处。
2. 多击判别依赖「`onMultiPress` ⇒ 同一次 `powerPress`」这一调用关系。宿主 OTA 若改动
   该关系，TTL 兜底能防住「单击永久失效」，但双击可能重新误熄屏 —— 届时看日志
   `FakeScreen: onMultiPress` 是否与 `applyDisplayPower` 成对出现即可定位。
3. 本功能只接管电源键，**不接管**系统的睡眠唤醒决策。来电 / 闹钟不亮屏是**设计选择**
   （见 §5.3），不是缺陷。
4. 系统接管屏幕时我们只**清标记、不抢屏**：若系统正处于「点亮动画中途」，
   我们不做任何干预，屏幕由系统完整接管。
5. 待命（磁贴打开）但屏幕亮着时**不延长超时**：系统会按用户设定正常熄屏。
   这是刻意的（见 §6.3），代价是「打开磁贴后放在桌上不动」等同于「普通待机」，
   只有真正按下电源键进入假熄屏后才开始挂机保护。
6. `armed` 存在 `Settings.Global`，重装模块 / 刷机后该键可能残留。影响仅限于
   「磁贴显示为开」，点一下即纠正，无功能副作用。
